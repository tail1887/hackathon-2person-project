## 2. 종합 판정

목업으로서의 기본 구조는 **부분 충족**이다. 화면별 렌더링 함수와 무승부 협상 명령이 분리되어 있고, D2026-09-19-14의 발신 대기 잠금·카운터오퍼 표시·협상 기록을 상태와 UI에 반영했다. 다만 카운터오퍼를 보낸 뒤 기존 제안을 수락할 수 있는 상태 전이 누락이 있어, 확정된 협상 규칙을 완전히 충족하지 못한다.

단일 HTML 목업이라는 범위에는 현재의 전역 상태와 직접 DOM 조작이 허용되지만, 실제 구현의 기준 구조로 승격하기에는 도메인 상태·화면 임시 상태·렌더링 책임이 한 파일과 전역 변수에 섞여 있다.

| 구분 | 판정 | 요약 |

| 목업 코드 구조화 | 부분 충족 | 화면별 렌더링·행동 함수는 분리됐으나, 전역 가변 상태와 도메인 규칙이 UI 함수에 결합됨 |

## 5. 발견 항목과 권장 보완

### P01 · 카운터오퍼 뒤 기존 제안 수락 가능 · 보완 필요

- **문제:** 수신자가 카운터오퍼를 보내면 활성 제안은 `counter_requested`가 된다. 그러나 수신자 화면은 여전히 조건 선택·`수락` 버튼을 보여 주며, `acceptNegotiation`은 제안 상태와 수락자의 역할을 검사하지 않는다.
- **영향:** 카운터오퍼 후에는 제안자가 새 버전을 낸다는 확정 흐름을 건너뛰고, 수신자가 이전 조건으로 합의를 확정할 수 있다. 이전 제안은 카운터오퍼 뒤 수락·선택할 수 없다는 시스템 정의와 충돌한다.
- **근거:** [시스템·데이터 정의](../../3_시스템_데이터_정의.md) 4.4의 `counter_requested` 규칙 및 [`mockup/index.html`](../../../mockup/index.html)의 `renderResponderForm`·`acceptNegotiation`.
- **권장 보완:** `renderNegotiation`과 `acceptNegotiation`에서 `status === 'open'` 및 “현재 사용자가 제안자의 상대”인지 함께 검사한다. `counter_requested`인 수신자 화면은 “제안자의 수정 대기” 읽기 전용 상태로 바꾸고, 기존 조건 선택·수락·추가 카운터오퍼를 숨긴다.
- **재검증 조건:** A 제안 → B 카운터오퍼 → B가 협상 화면을 다시 열어도 수락·추가 카운터오퍼가 불가능함을 확인한다. A가 새 버전을 보내면 B에 새 선택·수락 UI가 다시 나타나야 한다.

### R01 · 전역 상태와 화면·도메인 규칙의 결합 · 페이즈 2·3 전 구조화 권장

- **관찰:** 하나의 `state` 객체와 별도 전역 `proposerTempConditions`에 협상·미션·문철·화면 이력이 함께 저장되고, 명령 함수가 상태 변경·권한 판단·DOM 갱신·알림을 동시에 처리한다.
- **영향:** 현재 목업에는 적합하지만, 상태가 늘어나거나 실시간 이벤트를 붙이면 허용 전이를 한곳에서 검증하기 어렵고, 화면 전환·시나리오 로더가 상태를 우회해 바꾸는 위험이 생긴다.
- **권장 보완:** 페이즈 2·3 시작 전에 `settlement` 전이 함수(제안·카운터·수락·취소), 화면 임시 입력, 렌더링을 구분한다. 각 전이 함수는 현재 사용자·제안 상태를 받아 새 상태 또는 거절 결과만 반환하고, UI 함수는 그 결과를 표시하도록 둔다.
- **상태:** 설계 보완 항목. 현재 목업의 즉시 완료 조건을 막지는 않지만 P01을 수정할 때 함께 적용하면 재발 위험을 줄일 수 있다.

## 6. 미검증 항목과 남은 위험

- 로컬 파일 브라우저 자동 새로고침이 보안 정책으로 차단되어, 이번 검증에서는 클릭 기반 재현 대신 정적 흐름 대조를 수행했다.
- 이력의 시간·작성 시각·서버 순번은 목데이터에 없다. 실제 구현에서는 시스템 정의의 `room_revision`과 이벤트 순서를 사용해야 한다.
- 목업의 수락·카운터오퍼 권한 검사는 UI 수준이다. 실제 서비스에서는 서버가 방 멤버·제안 상태·수락자 권한을 원자적으로 검증해야 한다.
- M1.2의 페이즈 2·3과 M1.3 구현이 남아 있으므로, 이 보고서는 M1.2 전체 완료 판정이 아니다.
