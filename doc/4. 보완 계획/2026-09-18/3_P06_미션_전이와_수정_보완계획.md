# P06 미션 전이와 수정 보완계획

> 상태: 확정 · 시스템·데이터 정의 및 MVP 명세 반영 완료 · 2026-09-18

## 1. 목적과 범위

이 문서는 [M1.1 시스템·데이터 정의 검증보고서 v2의 P06](../../3.%20검증보고서/M1.1_시스템·데이터_정의/v2_검증보고서.md)인 **미션 전이·포기** 문제의 원인과 보완 방향을 정리한다.

대상은 무승부 합의 뒤 생성된 개인·공동 미션의 완료 요청, 재수행 요청, 포기, 그리고 양측 동의로 미션 내용·기한·수행자·개인/공동 유형을 수정하는 흐름이다. 새 미션을 만드는 무승부 협상 규칙이나 이미 `completed`·`abandoned`가 된 미션을 다시 여는 기능은 이 계획의 범위가 아니다.

## 2. 현재 문제 분석

현재 데이터 모델에는 `in_progress`, `completion_requested`, `counterpart_review`, `completed`, `revision_requested`, `abandoned` 상태가 함께 있으나, 상태 전이 그림은 `completion_requested` 대신 `counterpart_review`를 사용한다. 따라서 완료 요청 뒤 실제 저장 상태가 무엇인지 일관되지 않다.

또한 `revision_requested`가 된 뒤 수행자가 언제 `in_progress`로 돌아가는지, 공동 미션의 한 참여자가 포기하면 어떤 결과가 되는지 정의돼 있지 않다. 확정된 미션을 현실에 맞춰 바꾸는 경우에도, 새 무승부 협상을 다시 시작해야 하는지와 합의 전 원래 미션을 어떻게 보존하는지가 없다.

| 사례 | 현재 규칙의 공백 | 사용자 영향 |
| --- | --- | --- |
| 개인 수행자가 완료 요청 | `completion_requested`와 `counterpart_review` 중 어떤 상태를 저장할지 모호하다. | 화면·이벤트·권한 구현이 서로 달라질 수 있다. |
| 상대가 재수행 요청 | `revision_requested` 뒤 재수행을 시작하는 명령과 상태가 없다. | 미션이 재수행 요청 화면에 멈춘다. |
| 공동 미션에서 A가 포기 | B의 완료 체크인과 미션 종료를 어떻게 처리할지 없다. | 공동 미션이 한쪽 화면에서는 진행, 다른 쪽에서는 포기로 보일 수 있다. |
| 기한·문구·수행자를 바꾸고 싶음 | 새 무승부 협상으로 돌아가야 하는지, 기존 합의가 언제 바뀌는지 없다. | 사소한 현실 조정도 과도하게 무거워지거나 한쪽이 일방 변경할 위험이 있다. |

## 3. 보완 목표와 원칙

1. 미션 상태마다 다음 행동과 권한을 하나로 정한다.
2. 개인 미션의 완료 확인과 재수행 요청은 상대 확인자가 결정한다.
3. 공동 미션은 두 참여자의 완료 체크인이 모두 있어야 성공하며, 한 명의 포기는 공동 성공을 막는다.
4. 확정 미션의 문구·기한·수행자·개인/공동 유형은 수정 제안과 상대 수락이 모두 있어야 바꾼다.
5. 수정 제안이 수락되기 전에는 기존 미션과 기존 책임이 그대로 유효하다.
6. 이전 미션 내용과 수정 제안의 이력은 남기되, 완료된 미션을 임의로 다시 열지는 않는다.

## 4. 확정 보완안

### 4.1 상태와 기본 전이

`completion_requested`를 개인 미션의 **상대 확인 대기**를 뜻하는 유일한 저장 상태로 사용한다. `counterpart_review`는 별도 데이터 상태로 두지 않고, `completion_requested`를 보여 주는 화면 단계로만 취급한다.

```text
합의된 조건 → in_progress

개인 미션
  in_progress → completion_requested → completed
                                  └→ revision_requested → in_progress
  in_progress 또는 revision_requested → abandoned

공동 미션
  in_progress + 두 참여자의 joint_checkin → completed
  in_progress → abandoned  (참여자 중 한 명의 포기)
```

- 개인 미션은 `owner_user_id`가 완료 요청 또는 포기를 할 수 있다. 상대만 완료 확인 또는 재수행 요청을 할 수 있다.
- `revision_requested`에서 수행자가 `재수행 시작`을 누르면 `in_progress`로 돌아간다. 이전 완료 요청은 이력으로 남되 현재 완료 요청으로 취급하지 않는다.
- 공동 미션의 각 참여자는 자기 `joint_checkin`만 남길 수 있다. 두 사람의 현재 미션 버전에 대한 체크인이 모두 있어야 `completed`가 된다.
- 공동 미션에서 한 참여자가 포기하면 즉시 `abandoned`가 된다. 다른 참여자의 이전 체크인은 이력으로만 남고 공동 미션 성공에는 쓰지 않는다. `abandoned` 미션을 다시 열거나 대체 미션을 만드는 규칙은 이 계획의 범위 밖이다.

### 4.2 양측 수락형 미션 수정 제안

`in_progress` 또는 `revision_requested` 상태의 미션에서 방 멤버 누구나 수정 제안을 하나 만들 수 있다. 수정 제안에는 현재 미션 버전과 제안한 전체 값(문구, 기한, 수행자, 개인/공동 유형)을 함께 저장한다.

| 항목 | 규칙 |
| --- | --- |
| 제안 가능자 | 해당 방의 두 멤버 모두 |
| 수정 가능 범위 | 문구, 기한, 개인 미션 수행자, 공동 미션 참여자, 개인/공동 유형 |
| 동시 제안 | 미션마다 `open` 수정 제안은 최대 1개 |
| 수락 | 제안자가 아닌 상대만 수락할 수 있으며, 수락 시에만 수정값을 현재 미션에 적용 |
| 거절·취소 | 상대가 거절하거나 제안자가 취소하면 기존 미션을 그대로 유지 |
| 종료 상태 | `completed`, `abandoned`, `completion_requested`에서는 새 수정 제안을 만들 수 없음 |

수락은 한 성공/실패 단위에서 수정 제안 상태를 `accepted`로 바꾸고, 미션의 현재 버전을 1 증가시키고, 제안한 필드를 적용한다. 기존 완료 요청과 공동 완료 체크인은 새 버전에 넘기지 않으며, 수정된 미션은 `in_progress`로 시작한다. 수락 직전에 미션이 완료·포기됐거나 현재 버전이 달라졌으면 수락하지 않고 수정 제안을 `stale`로 처리한다.

### 4.3 수정 이력과 권한 검사

논리 데이터 모델에 아래 두 단위를 추가한다.

| 엔터티 | 필수 필드 | 상태/제약 |
| --- | --- | --- |
| 미션 버전 (`mission_revision`) | `id`, `mission_id`, `revision`, `text`, `due_date`, `kind`, `owner_user_id`, `participant_user_ids`, `applied_at` | 현재 적용된 미션 값의 이력. 같은 미션 안에서 `revision`은 중복 없이 증가한다. |
| 미션 수정 제안 (`mission_change_offer`) | `id`, `mission_id`, `base_revision`, `proposer_user_id`, `proposed_text`, `proposed_due_date`, `proposed_kind`, `proposed_owner_user_id`, `proposed_participant_user_ids`, `status`, `created_at`, `resolved_at` | `open`, `accepted`, `rejected`, `cancelled`, `stale`. 현재 허용 상태에는 `open` 1개만 둔다. |

서버는 로그인한 사용자와 저장된 방 멤버·현재 미션 버전으로 제안·수락 권한을 검사한다. 클라이언트가 보낸 수행자, 참여자, 이전 상태나 버전만 믿고 수정값을 적용하지 않는다. 수정 제안·수락·거절·취소·만료는 방 공용 기록과 이벤트로 두 참가자에게 동시에 반영한다.

## 5. 대안과 권장 이유

| 안 | 방식 | 장점 | 한계 |
| --- | --- | --- | --- |
| A | 확정된 미션은 수정 불가, 새 무승부 협상만 허용 | 합의 원본이 단순하게 유지된다. | 기한·문구 같은 현실적인 조정에도 협상 전체를 다시 시작해야 한다. |
| B | 어느 한쪽이 미션을 즉시 수정 | 조작이 빠르다. | 이미 합의한 책임·기한을 일방적으로 바꿀 수 있다. |
| C | 양측 수락형 수정 제안, 수락 전 기존 미션 유지 | 합의의 효력을 지키면서 필요한 조정을 가볍게 처리한다. | 수정 제안·버전·이력 규칙을 추가해야 한다. |

MVP에는 **C안**을 적용한다. 커플이 상황에 맞게 합의 내용을 바꿀 수 있어야 하지만, 미션은 양측 합의로 만들어졌으므로 어느 한쪽도 즉시 바꿀 수 없어야 한다.

## 6. 재검증 시나리오와 완료 기준

| 시나리오 | 기대 결과 |
| --- | --- |
| 개인 수행자가 완료 요청 | 상태는 `completion_requested` 하나로 저장되고, 상대에게 확인·재수행 요청만 보인다. |
| 상대가 재수행 요청 후 수행자가 재수행 시작 | `revision_requested`에서 수행자의 명시적 시작 행동으로 `in_progress`가 된다. |
| 공동 미션에서 A만 완료 체크인 | 미션은 `in_progress`이며 B의 체크인을 기다린다. |
| 공동 미션에서 A가 포기 | 즉시 `abandoned`가 되며 B의 체크인만으로 완료될 수 없다. |
| A가 문구·기한·수행자를 바꾼 수정 제안을 생성 | 수락 전에는 기존 미션의 값·책임·상태가 계속 적용된다. |
| B가 수정 제안을 수락 | 새 미션 버전이 적용되고 이전 완료 요청·체크인은 무효화되며 `in_progress`가 된다. |
| B가 수정 제안을 거절하거나 A가 취소 | 기존 미션은 전혀 바뀌지 않는다. |
| 수정 제안 대기 중 미션이 완료 또는 포기됨 | 제안은 `stale`이 되고 수정값을 적용할 수 없다. |

다음 조건을 모두 만족하면 P06을 문서상 해소로 바꾼다.

- `completion_requested`, `revision_requested`, `in_progress`의 저장 상태와 전이가 하나로 정리돼 있다.
- 개인·공동 미션의 완료·포기 행동, 권한, 결과가 모두 정의돼 있다.
- 수정 제안의 생성·수락·거절·취소·만료와 수락 전후 미션 값의 규칙이 정의돼 있다.
- 수정 제안과 미션 버전의 이력·동시성 검사가 데이터 모델과 공용 이벤트에 연결돼 있다.

## 7. 후속 구현에서 정할 항목

- 수정 제안 화면에서 변경 전·후 값을 어떤 비교 형태로 보여 줄지
- 수정 제안에 사유 메시지를 필수·선택 중 무엇으로 둘지
- 기한이 지난 미션의 수정·재수행·포기 화면 규칙
- M1.2 인터페이스 계약에서 수정 제안과 상태 전이 명령의 정확한 요청·응답 필드, 충돌 오류 문구
