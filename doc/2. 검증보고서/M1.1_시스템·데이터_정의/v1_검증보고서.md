# M1.1 시스템·데이터 정의 검증보고서 v1

> 상태: 완료 전 검증 · 보완 필요 · 2026-09-17

## 검증 범위

- 대상: [3번 시스템·데이터 정의](../../3_시스템_데이터_정의.md)의 데이터 모델, 상태 전이, 접근 권한, 실시간 동기화 규칙.
- 기준: [MVP 명세](../../1_MVP_명세.md), [마일스톤 계획](../../2_마일스톤_계획.md)의 M1.1 완료 기준.
- 방법: 문서 내부 규칙 대조와 두 사용자 시나리오 추적. 코드 실행이나 실제 두 브라우저 테스트는 수행하지 않았다.
- 판정: 기본 구성은 정의되어 있으나 권한 충돌과 상태·책임 규칙의 누락이 있어, 현재 문서만으로 M1.1 완료를 확인할 수 없다.
- 이 보고서의 보완 방향은 검토 제안이다. 제품 정책을 확정하거나 원본 시스템 문서를 수정한 것은 아니다.
- 이후 로그인 필수 전환, 작성자 전용 초안·AI 심판 기록 보관, 개인 기록 삭제 결정으로 사용자 식별·초대 입장·비공개 이벤트·삭제 규칙이 바뀌었다. P01·P04·P05를 포함한 권한 항목은 변경된 [시스템·데이터 정의](../../3_시스템_데이터_정의.md)를 기준으로 다시 검증해야 한다.

### P01. 입장 전 사용자에게 적용할 권한 예외가 없다

- **근거:** §5는 모든 조회·명령에 방 멤버 검사를 먼저 적용하지만, §2.2의 초대 수락자는 아직 멤버가 아니다. 방 생성 시에도 기존 멤버십이 없다.
- **영향:** 공통 검사를 그대로 적용하면 정상적인 방 생성·초대 검증·입장을 거절할 수 있다.
- **보완 방향:** 방 생성은 세션과 진행 중인 방 제한, 초대 검증·수락은 유효 초대와 빈자리 등을 검사하도록 방 내부 명령과 구분한다.
- **재검증 기준:** 신규 사용자의 생성·입장은 가능하고, 미가입 사용자의 기존 방 메시지 조회는 거절되는 규칙이 함께 명시된다.

### P02. 카운터오퍼에서 기존 조건의 수행 책임이 모호하다

- **근거:** 개인 미션 책임자를 “조건을 낸 제안자”로 정의하지만, 카운터오퍼마다 제안자는 바뀐다. MVP는 기존 조건 유지도 허용한다.
- **예시:** A가 “A가 밥 사기”를 제안하고 B가 기한만 바꾼 경우, 새 제안자가 B라는 이유로 책임자도 B가 되는지 불명확하다.
- **영향:** 합의한 의도와 다른 사람에게 미션이 배정될 수 있다. 책임자 필드는 있지만 이를 버전 간 유지·변경하는 규칙이 없다.
- **보완 방향:** 기존 조건의 책임자 보존과 새 조건의 책임자 지정, 책임자 변경 시 합의 규칙을 구분한다.
- **재검증 기준:** 조건 유지·추가·수정 각각에서 최종 책임자를 두 사용자 관점으로 추적할 수 있다.

### P03. 안전 안내 이후 전송과 대국 중단의 의미가 불명확하다

- **근거:** §4.2는 처리 상태 `ready`와 결과 유형 `safety_guidance`를 분리한다. 본문은 안전 안내 시 일반 추천을 제공하지 않고 대국 중단 선택지를 보인다고 한다. §3은 `closed`를 MVP에서 생성하지 않는다고 명시한다.
- **영향:** 프런트엔드와 서버가 위험 원문의 전송 허용 여부를 다르게 구현할 수 있다. 중단 버튼이 화면만 닫는지, 대화를 일시 중지하는지, 방을 종료하는지도 정할 수 없다.
- **보완 방향:** 안전 안내 상태에서 허용할 행동과 서버 전송 조건을 팀이 결정하고, 중단의 범위·상대 화면 영향·재개 가능 여부를 명시한다. 이 보고서는 허용 또는 차단 정책을 대신 결정하지 않는다.
- **재검증 기준:** 위험 표현 감지 → 안내 → 가능한 버튼 → 서버 처리 → 양쪽 화면의 결과가 하나의 흐름으로 정의된다.

### P04. 비공개 변경과 방 공용 순번의 복구 규칙이 부족하다

- **근거:** §6은 방 단위 `room_revision`과 누락 변경 재조회를 사용하지만, AI 심판 이벤트는 요청자에게만 보낸다.
- **예시:** A에게만 분석 결과가 전달된 뒤 공용 메시지가 도착하면 B가 받은 순번에는 간격이 생길 수 있다.
- **영향:** 순번 간격을 모두 이벤트 유실로 처리하면 불필요한 복구가 반복될 수 있다. 재조회에서도 분석별 공개 범위를 적용해야 한다.
- **보완 방향:** 비공개 변경의 순번 처리, 사용자별 조회 결과와 복구 완료 기준을 정의한다. 비공개 변경을 제외하더라도 동기화가 완료됨을 판단할 수 있어야 한다.
- **재검증 기준:** A만 분석 요청 → B 연결 끊김·재접속 → 공용 메시지 수신 사례에서 비공개 결과 노출 없이 두 화면이 같은 공용 상태로 복구된다.

### P05. 표시 이름과 내부 식별자·접근 권한이 혼재되어 있다

- **근거:** §2.1은 화면과 이벤트에 ID 대신 표시 이름만 노출한다고 하지만, §3 데이터에는 발신자·수행자 ID가 있다. §5는 표시 이름과 세션을 한 행으로 묶어 본인만 읽도록 정의한다.
- **영향:** 같은 이름의 두 사용자를 구분하는 방식이 불명확하고, 상대 이름 표시와 이름 읽기 권한도 일치하지 않는다.
- **보완 방향:** 화면용 이름, 데이터 연결용 식별자, 비밀 세션 정보를 구분하고 각각의 공개 범위를 명시한다. 세션 비밀을 이벤트로 보내는 방식은 사용하지 않는다.
- **재검증 기준:** 같은 표시 이름이어도 메시지 발신자·미션 수행자를 구분하며, 상대 표시 이름은 볼 수 있고 세션 비밀은 공유되지 않는다.

### P06. 미션의 상태 목록과 전이·포기 규칙이 일치하지 않는다

- **근거:** §3의 `completion_requested`는 §4.5 전이에서 사용하지 않는다. `revision_requested`에서 `in_progress`로 돌아가는 계기가 없고, 공동 퀘스트 포기 권한·결과도 정의되지 않았다.
- **영향:** 완료 요청과 확인 대기를 중복 상태로 구현하거나, 다시 요청·포기 이후 양쪽 화면의 상태가 달라질 수 있다.
- **보완 방향:** 실제로 저장할 상태와 단순 행동을 구분하고, 다시 요청·공동 포기의 실행 주체와 전이 결과를 명시한다.
- **재검증 기준:** 개인·공동 미션의 허용 행동마다 이전 상태, 실행자, 다음 상태가 하나로 정해진다.

### P07. 사진을 확인할 상대의 읽기 권한이 불명확하다

- **근거:** §5는 사진을 “해당 미션 참여자”만 읽도록 하지만, 개인 미션의 수행자와 확인자는 다르다. 개인 미션의 참여자 필드에 확인자가 포함되는지도 정의되지 않았다.
- **영향:** 사진 인증을 구현하면 정작 완료를 확인할 상대가 사진을 열지 못할 수 있다.
- **보완 방향:** 개인 미션의 상대 확인자에게 사진 읽기를 허용하는지 명시한다. 공동 퀘스트의 사진 완료 방식도 개인 미션과 구분한다.
- **재검증 기준:** 수행자·상대 확인자·방 외부 사용자의 사진 접근 결과가 각각 정의된다. 사진 기능을 제외하면 필수 텍스트 완료 경로에는 영향을 주지 않는다.

## 미검증 항목과 남은 위험

- P01~P06은 핵심 권한·상태 규칙 보완 후 문서 재검증이 필요하다. P07은 사진 인증을 구현할 경우 확인한다.
- 문서 검토만 수행했으므로 실제 권한 차단, 동시 입장·수락, 이벤트 유실 복구, AI 결과 및 안전 분류 동작은 검증하지 않았다. 구현 단계에서 테스트가 필요하다.
- 초대 만료·재발급, 세션 손실 이후 처리, `오늘/내일`의 기준 시간대는 후속 계약에서 명확히 해야 한다.
- 조건 0개 합의 시 조건별 생성 규칙에 따르면 미션도 0개가 된다. 이 경우의 합의 완료 화면을 M1.2에서 정의해야 한다.
- 서버 기술·저장소·실시간 전송 제품의 선택은 M1.3 범위이며 이번 검증의 실패 사유로 판단하지 않았다.
- [의사결정 로그](../../0_커플들이_집착하는_AI_심판이_되었다_기획서.md#14-의사결정-로그)를 확인했다. 이번 변경은 문제 보고와 링크 추가로, 새로운 정책 결정이 없어 로그를 추가하지 않았다. 보완 과정에서 정책을 확정하면 해당 결정을 기록해야 한다.
