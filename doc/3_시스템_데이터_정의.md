# 커플들이 집착하는 AI 심판이 되었다 — M1.1 시스템·데이터 정의

> **상태: 초안 · 2026-09-17**
>
> 이 문서는 [MVP 명세](1_MVP_명세.md)의 고정 데모 시나리오를 구현하기 위한 논리 시스템·데이터 계약이다. DB, 실시간 전송 수단, AI 제공사 같은 기술 선택은 M1.3에서 결정한다.

---

## 1. 범위와 시스템 경계

### 1.1 M1.1이 다루는 것

- 로그인 계정 두 명의 대국방 연결과 미션 재진입
- 메시지, AI 심판, AI 문철, 무승부 협상, 미션의 저장 단위와 상태
- 대국방 멤버만 데이터를 읽고 바꾸게 하는 권한 규칙
- 두 브라우저가 같은 순서의 확정 데이터를 보게 하는 실시간 동기화 규칙

### 1.2 이번 단계에서 선택하지 않는 것

- 프런트엔드·백엔드·DB·인증·실시간·AI·배포 제품과 라이브러리
- 사진 첨부·사진 인증 기능과 파일 저장소·AI 이미지 판별 방식(MVP 범위에서 제외)
- 장기 보관, 계정 복구, 탈퇴·삭제의 운영 정책

### 1.3 논리 구성

```text
두 브라우저
  │ 명령 요청 / 상태 조회
  ▼
애플리케이션 서버 ── AI 분석 요청 ── AI 서비스
  │ 검증 후 확정 데이터 기록
  ├── 영속 데이터 저장소
  └── 실시간 이벤트 전송 ── 대국방의 두 브라우저
```

- 서버가 메시지·협상·미션의 유일한 확정 주체다. 클라이언트의 임시 입력이나 화면 상태는 사실로 취급하지 않는다.
- AI는 필요한 대화 맥락과 입력만 받아 분석 결과를 돌려준다. AI 결과는 약속·합의·미션을 스스로 확정할 수 없다.
- 기술 선택 전에는 `명령 요청`, `상태 조회`, `실시간 이벤트`라는 논리 경계만 사용한다. 구체 API와 이벤트 형식은 M1.2에서 정한다.

## 2. 식별과 접근 모델



### 2.1 로그인 계정 사용자

대국방 생성과 초대 수락은 로그인한 `사용자`만 할 수 있다. 사용자는 카카오·구글 간편 로그인 또는 이메일·비밀번호 회원가입으로 계정을 만든다. 카카오 인증에 성공했지만 이메일 동의를 제공하지 않은 사용자도 로그인 사용자로 취급하며, 이메일은 이메일·비밀번호 회원가입에만 필수다. 대국방 안에서는 방 입장 때 확정한 표시 이름과 방 전용 참가자 식별 키만 상대에게 노출한다. 내부 `user.id`는 화면과 실시간 이벤트에 보내지 않는다.

계정에 연결된 인증 세션은 기술 구현과 무관하게 다음 권한 판단에 필요하다.

- 방을 만든 사람은 `creator`, 초대로 입장한 사람은 `invitee` 역할을 가진다.
- 역할보다 **대국방 멤버인지 여부**가 기본 접근 조건이다. 두 역할의 메시지·협상·미션 권한은 동등하다.
- 한 로그인 계정은 진행 중인 대국방을 하나만 가진다. 새 방 생성과 초대 입장 시점에 이 조건을 다시 확인하며, 제한을 넘으면 아무 상태도 바꾸지 않고 거절한다.
- 합의가 확정되면 방은 `closed`가 된다. 종료된 방의 두 멤버는 메시지·AI·협상을 새로 만들 수 없고, 기존 공용 기록과 합의 결과만 읽을 수 있다. 미션 처리 권한은 방 종료 뒤에도 유지된다.
- 사용자는 같은 계정으로 다시 로그인해 진행 중인 방과 미션에 재진입한다. 브라우저를 바꾸거나 세션이 만료되어도 계정 인증 뒤 권한이 복구된다.
- 외부 제공자의 식별자와 이메일·비밀번호 인증 정보는 대국방 상대에게 노출하지 않는다.
- `room_member`의 방 전용 `public_member_key`는 해당 방에서만 참가자를 구분한다. 다른 방에서 재사용하거나 사용자 검색·계정 식별에 쓰지 않는다.
- 두 참가자의 방 표시 이름이 다르면 화면에는 이름만 보인다. 같으면 두 사람 모두 `표시 이름 · A/B`처럼 방 안의 보조 표기를 붙인다. 이 표기는 메시지 발신자, 협상 제안자·조건 책임 주체, 미션 수행자·확인자, 활동 기록에 동일하게 쓴다.
- 프로필 표시 이름을 바꿔도 기존 방의 이름·보조 표기는 바꾸지 않는다. 새로 생성하거나 입장하는 방에서만 새 표시 이름을 복사한다.
- 로그인한 사용자는 메인의 `내 프로필`에서 자신의 `display_name`만 확인·수정한다. 인증 제공자 식별자·비밀번호·내부 `user.id`는 이 화면에 표시하거나 수정하지 않는다.
- MVP의 아바타는 `display_name`과 사용자 ID에서 결정되는 이니셜·기본 색상 표시이며 이미지 파일을 저장하지 않는다. UI는 이후 선택적 `avatarUrl`을 표시할 수 있으나, 데이터 필드·Storage·업로드 권한은 사진 기능을 추가할 때 함께 정의한다.



### 2.2 초대

방 생성 시 한 개의 `초대`를 만들고, 공유 링크용 비밀 토큰과 사람이 입력할 6자리 코드를 함께 발급한다. 둘은 같은 초대를 가리킨다. 초대 코드 입력을 포함한 모든 기능은 로그인 뒤에만 제공한다. 로그인하지 않은 사용자가 링크를 열면 인증을 마친 뒤 원래 링크로 돌아가 초대를 수락할 수 있어야 한다.

- 링크 토큰은 충분히 추측하기 어렵게 생성하고 저장 시에는 원문 대신 검증 가능한 값만 보관한다.
- 6자리 코드는 활성 초대 안에서 충돌하지 않아야 하며, 충돌 시 다시 생성한다.
- 초대 수락은 초대가 활성 상태이고 방의 두 번째 자리가 비어 있을 때만 성공한다. 성공하면 초대는 `사용됨`이 되고 추가 입장은 모두 거절한다.
- 미로그인 초대 링크 방문은 서버에 초대 확인 요청을 보내지 않고 로그인·회원가입 화면으로 이동한다. 방 ID·참가자 이름·방 상태·대화 내용·초대 유효성은 인증 전 반환하거나 표시하지 않는다.
- 인증 성공 뒤 브라우저는 사용자를 원래 초대 링크로 돌려보낸다. 로그인한 사용자가 링크를 열거나 시작 화면에서 6자리 코드를 입력하면, 서버는 초대 상태·빈자리·진행 중인 방 제한을 확인한다. 코드 확인 요청은 무차별 대입을 막을 수 있도록 구현 단계에서 횟수를 제한한다.
- 모든 검사를 통과하면 서버는 초대받은 사용자를 방 멤버로 추가하고, 초대를 `사용됨`으로 바꾸고, 방을 `진행 중`으로 바꾼 뒤 대국방으로 이동시킨다. 셋 중 하나라도 처리할 수 없으면 세 상태를 모두 이전 그대로 두고 방으로 이동시키지 않는다. 로그인한 수락자에게만 `만료/해제`, `이미 사용됨 또는 정원 초과`, `내 진행 중 대국 존재`, `유효하지 않음`을 구분해 안내하며, 어떤 실패에서도 방 이름·멤버·대화·협상 정보는 반환하지 않는다.

## 3. 논리 데이터 모델

공통 필드 `id`, `created_at`, `updated_at`은 필요한 엔터티에 둔다. 시간은 서버가 기록한 시각을 기준으로 하며, 표시용 시간대 변환은 클라이언트가 한다.


| 엔터티                           | 필수 필드                                                                                                                                                                                                | 상태/제약                                                                                                                                                                                                                             |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 사용자 (`user`)                  | `id`, `display_name`, `account_status`, `created_at`                                                                                                                                                 | 계정 표시 이름. 방에서는 입장 시 `room_member.room_display_name`으로 복사해 사용한다. 진행 중인 방은 로그인 계정당 1개다.                                                                                                                                                                                       |
| 인증 수단 (`auth_identity`)       | `id`, `user_id`, `provider`, `provider_subject`, `email_normalized`, `password_digest`, `verified_at`, `linked_at`                                                                                   | `provider`: `kakao`, `google`, `local`. 간편 로그인은 제공자 식별자를, 일반 회원가입은 이메일과 비밀번호 해시를 사용한다. `email_normalized`는 카카오 등 제공자가 이메일을 주지 않으면 비어 있을 수 있으며, 일반 회원가입에서는 필수다. `(provider, provider_subject)`와 일반 회원가입 이메일은 각각 한 사용자에게만 연결하며, 비밀번호 원문은 저장하지 않는다.                                                 |

| 초대 (`invite`)                 | `id`, `room_id`, `code`, `link_token_digest`, `status`, `expires_at`, `used_by_user_id`, `used_at`                                                                                                   | `active`, `used`, `expired`, `revoked`. MVP에서는 방당 활성 초대 1개다.                                                                                                                                                                      |
| 메시지 초안 (`message_draft`)      | `id`, `room_id`, `author_user_id`, `body`, `revision`, `status`, `sent_message_id`, `saved_at`, `private_record_deleted_at`                                                                           | 작성자만 읽는 비공개 초안. `active`, `sent`, `discarded`, `private_record_deleted`; 수정할 때마다 `revision`을 증가시킨다. 같은 방·작성자 조합의 `active` 초안은 1개이며, 전송된 초안은 보관하고 메시지와 연결한다.                                                                       |

| AI 문철 신청 (`room_review_request`) | `id`, `room_id`, `requester_user_id`, `responder_user_id`, `context_through_sequence`, `status`, `requested_at`, `accepted_at` | 신청자는 자신의 동의를 표시한다. 상태는 `pending`, `accepted`, `processing`, `ready`, `failed`, `cancelled`이며, `pending`에서는 `room_review` 분석을 만들지 않는다. 상대 수락 뒤에만 분석을 생성한다. 최초 분석 실패의 `failed`는 두 멤버에게 공용으로 보이며 신청자만 같은 요청을 한 번 재시도하거나 취소할 수 있다. 재시도 실패 또는 취소는 `cancelled`가 된다. 준비 완료 알림의 사용자별 확인 상태는 공용 신청 데이터와 분리해 사용자 전용 상태로 보관한다. |
| AI 분석 (`ai_analysis`)         | `id`, `room_id`, `requester_user_id`, `draft_id`, `draft_revision`, `type`, `visibility`, `input_hash`, `context_through_sequence`, `result_type`, `result`, `status`, `private_record_deleted_at` | `type`: `message_mediation`/`private_position`/`room_review`. `message_mediation`의 사용자 표시명은 AI 심판이다. `draft_id`·`draft_revision`은 `message_mediation`에만 사용한다. `private_position`은 요청자만 보는 형세 파악으로 `visibility: private`, `room_review`는 함께 읽는 AI 문철로 `visibility: room`이다. `room_review.result`는 `shared_summary`, `different_points`, `inferred_hopes_and_worries`, `next_moves`를 구조화해 저장한다. 처리 상태 `status`: `pending`, `ready`, `stale`, `failed`; 결과 유형 `result_type`: `normal`, `restricted`. |
| 협상 (`settlement`)             | `id`, `room_id`, `status`, `active_offer_id`, `agreed_offer_id`                                                                                                                                      | 방당 `open` 상태 협상은 최대 1개. 상태는 `open`, `agreed`, `cancelled`.                                                                                                                                                                        |
| 협상 제안 버전 (`settlement_offer`) | `id`, `settlement_id`, `revision`, `proposer_user_id`, `selection_mode`, `status`, `accepted_by_user_ids`, `created_at`                                                                                              | `selection_mode`: `single`/`multiple`/`none`. 조건이 없으면 `none`; 제안에는 기한을 저장하지 않는다. 제안자는 생성과 동시에 수락한 것으로 기록한다. `status`: `open`/`counter_requested`/`accepted`. `open` 제안은 상대 응답 전 제안자가 수정·재발송할 수 없는 읽기 전용 버전이다. 카운터오퍼 메시지 뒤에도 제안자는 바뀌지 않는다.                                                                                                                                                                                |
| 협상 조건 (`settlement_term`)     | `id`, `offer_id`, `text`, `mission_kind`, `responsible_user_id`, `participant_user_ids`, `display_order`                                                                                             | 상대가 고를 조건 선택지. 제안자가 책임 주체를 `나`·`상대`·`함께` 중에서 명시한다. AI 추천 조건의 기본 책임 주체는 제안자지만 수정 가능하다. 저장할 때 `나`·`상대`는 해당 제안의 제안자·상대방 사용자 ID로 바꾼다. `mission_kind`: `individual`/`joint`; 개인은 `responsible_user_id` 한 명, 공동은 두 멤버를 `participant_user_ids`에 둔다. 조건은 0개 이상 가능하다.                                                                                                                               |
| 조건 선택 (`settlement_term_selection`) | `offer_id`, `selector_user_id`, `term_id`, `selected_at` | 제안자의 상대만 생성한다. `single`은 정확히 1개, `multiple`은 1개 이상 선택한다. 합의 뒤 선택한 조건만 미션의 원본 조건이 된다. |
| 카운터오퍼 메시지 (`settlement_counter_message`) | `id`, `offer_id`, `author_user_id`, `body`, `created_at` | 활성 제안의 상대만 생성한다. 조건·선택 방식의 수정값이 아니라 제안자에게 보내는 요청 메시지다. 원 제안 아래에 연결해 표시하며, 이 메시지가 있을 때만 제안자가 다음 버전을 생성할 수 있다. |
| 미션 (`mission`)                | `id`, `room_id`, `settlement_id`, `source_term_id`, `current_revision`, `kind`, `owner_user_id`, `participant_user_ids`, `text`, `due_date`, `status`                                                  | 합의된 제안의 조건마다 하나씩 생성한다. `in_progress`, `completion_requested`, `completed`, `revision_requested`, `abandoned`. `completion_requested`는 상대 확인 대기 상태다. |
| 미션 버전 (`mission_revision`) | `id`, `mission_id`, `revision`, `text`, `due_date`, `kind`, `owner_user_id`, `participant_user_ids`, `applied_at` | 현재 적용된 미션 값의 이력. 같은 미션 안에서 `revision`은 중복 없이 증가한다. |
| 미션 수정 제안 (`mission_change_offer`) | `id`, `mission_id`, `base_revision`, `proposer_user_id`, `proposed_text`, `proposed_due_date`, `proposed_kind`, `proposed_owner_user_id`, `proposed_participant_user_ids`, `status`, `created_at`, `resolved_at` | `open`, `accepted`, `rejected`, `cancelled`, `stale`. `in_progress`·`revision_requested` 미션에는 `open` 제안을 최대 1개 둔다. |
| 미션 수행 기록 (`mission_action`)   | `id`, `mission_id`, `revision`, `actor_user_id`, `type`, `note`, `created_at`                                                                                                                       | `complete_request`, `confirm`, `request_revision`, `resume`, `abandon`, `joint_checkin`. 행동은 해당 미션 버전에 연결한다. |




### 3.1 작성자 개인 기록

작성자 개인 기록은 `message_draft`, 그 초안에 연결된 `message_mediation` AI 분석, 요청자 전용 `private_position` 분석이다. 다른 사용자·방 공용 이벤트·공용 복기에는 포함하지 않는다.

- **작성 중 초안:** 내용이 있는 초안만 자동 저장해 같은 계정의 다른 기기에서도 이어 쓴다. 빈 작성창은 기록하지 않는다. 초안 본문은 작성자만 읽는다.
- **동시 수정 충돌:** 클라이언트는 마지막으로 서버가 확정한 초안의 `revision`을 `expected_revision`으로 보관한다. 자동 저장·명시적 저장·버림·AI 심판 요청은 이를 함께 보내며, 서버는 현재 `revision`과 같을 때만 처리한다. 같지 않으면 초안·분석·비공개 순번을 바꾸지 않고 작성자에게만 최신 초안의 본문·`revision`·갱신 시각을 담은 `draft_revision_conflict`를 반환한다. `revision`은 초안 내용의 기준 버전이고 `private_revision`은 비공개 변경 전달 순번이므로 서로 대신하지 않는다.
- **충돌 화면:** 충돌한 기기는 자동 저장을 멈추고 로컬의 미저장 입력을 기기 임시 상태에 보존한다. 사용자는 최신 초안을 사용해 로컬 입력을 버리거나, 최신 `revision`을 기준으로 자신의 변경을 다시 저장하거나, 최신 본문에서 직접 편집할 수 있다. 다른 기기의 `draft.updated`를 받았을 때 미저장 입력이 없으면 최신 초안을 적용하고, 있으면 작성창을 자동으로 바꾸지 않고 같은 선택지를 보여 준다. 오프라인 보류 저장도 기존 `expected_revision`으로 검사한다.
- **전송 뒤 기록:** 메시지를 전송하면 초안 상태는 `sent`가 된다. 원문 초안·AI 심판 결과를 전송 메시지에 연결해 보관하고, 작성자만 자신의 전송 메시지 본문을 눌러 같은 카드에서 `내 원문`, `AI 추천문`, `실제 전송: 원문/AI 추천문`을 펼친다. 이 연결과 상세값은 상대·방 공용 이벤트·무승부 협상 메시지에 공개하지 않는다.
- **전송 전 버림:** 사용자가 초안을 명시적으로 버리면 `discarded`가 되어 더 이상 열람하지 않는다.
- **전송 뒤 개인 기록 삭제:** 작성자가 개인 기록 삭제를 선택하면 초안 본문·AI 심판 결과를 비공개 저장값과 작성자 화면·이후 개인 복기에서 즉시 제거한다. 여러 기기에 삭제 상태를 동기화하기 위한 `private_record_deleted_at`만 남기며, 이 값에는 삭제한 내용이 들어 있지 않고 복기에 쓰이지 않는다. 전송된 메시지 본문·방 공용 순번·협상·미션은 바꾸지 않는다. 실제 보관·완전 삭제 기간은 M1.3에서 정한다.
- **AI 분석 연결:** AI 심판 분석은 원문을 중복 저장하지 않고 `draft_id`와 `input_hash`로 해당 초안을 연결한다. `normal` 결과의 추천 문구만 `result`에 저장한다. 개인 형세 파악은 요청 시점의 확정 메시지 순번을 `context_through_sequence`으로 남기며, 초안과 연결하지 않는다. `restricted`는 추천·안내 본문을 저장하지 않는 결과 유형이다.
- **비공개 동기화:** 초안 저장, AI 심판·개인 형세 파악 상태 변경, 개인 기록 삭제가 확정되면 해당 사용자·방의 `private_revision`을 1 증가시키고 `private_change`를 남긴다. 이 순번과 변경 목록은 작성자 본인의 다른 기기 복구에만 쓰며, 상대에게는 보내지 않는다.



### 3.2 임시 처리 정보

아래 정보는 사용자 기능을 처리하는 동안만 쓰며, 대화 기록·개인 복기·공용 복기의 데이터가 아니다.

- **AI 요청 조합:** 서버는 AI 심판 요청 때 최신 초안, 필요한 최근 메시지, 위험 입력에는 추천·재작성·협상 조건을 만들지 않고 `restricted`만 반환하라는 프롬프트 규칙을 잠시 묶어 AI 서비스에 보낸다. 이 요청 조합 자체는 별도 기록으로 저장하지 않는다. 완료 뒤 남기는 것은 3.1의 AI 분석 결과뿐이다.
- **접속 상태:** 상대의 온라인·오프라인 표시에 쓰는 일시 상태다. 메시지·협상·미션의 사실이나 대화 기록으로 보관하지 않는다.
- **초대 복귀 경로:** 미로그인 사용자가 초대 링크를 열면 브라우저는 원래 링크를 인증 완료 뒤 돌아갈 경로로만 일시 보존한다. 이때 서버는 토큰을 검증하거나 `pending_invite`를 만들지 않는다. 인증 성공 뒤 원래 링크를 다시 열어 로그인한 사용자에게 초대 수락 검사를 수행하며, 입장 성공·실패·취소 시 복귀 경로는 폐기한다. 구체 보존 방식과 변조 방지는 M1.3에서 정한다.

## 4. 상태 전이와 명령 규칙



### 4.1 대국방과 초대

```text
방 생성 → waiting + active 초대
상대가 유효한 링크/코드를 수락 → active + 초대 used
```

- `waiting` 방에서는 생성자만 입장해 있고, 초대 상태만 볼 수 있다. 메시지·AI 문철·협상은 `active` 뒤에 가능하다.
초대 수락이 성공하려면 다음 세 변경이 모두 함께 적용돼야 한다.

1. 초대받은 사용자를 방 멤버로 추가한다.
2. 해당 초대를 `사용됨`으로 바꾼다.
3. 방 상태를 `상대 대기`에서 `진행 중`으로 바꾼다.

방이 이미 찼거나 중간에 오류가 나면 세 변경을 하나도 적용하지 않는다. 즉, 사용자가 멤버로만 추가되거나 초대 코드만 소모되는 상태는 만들지 않는다.

### 4.2 AI 심판과 메시지

```text
초안 작성 → AI 심판 요청 → 분석 pending → ready
  ├→ result_type: normal → 원문 전송 / 추천 문구 전송 → 메시지 확정
  │                       또는 초안 수정 → 분석 stale → 다시 AI 심판 요청
  └→ result_type: restricted → 초안 수정 → 분석 stale → 다시 AI 심판 요청
```

- `AI 심판 요청`은 요청자의 저장된 초안과 최근 확정 메시지 맥락을 사용한다. 결과의 `visibility`는 항상 `private`다.
- 분석이 `ready`여도 `result_type`이 `restricted`일 수 있다. 이 경우 AI 심판 시트는 일반 추천·재작성·협상 조건을 제공하지 않고 `이 문장에는 AI 심판을 제공할 수 없습니다. 문장을 수정해 다시 확인해 주세요.`만 표시한다. `restricted` 분석으로는 원문·추천 문장을 전송할 수 없다.
- `초안 수정`은 현재 `revision`과 `expected_revision`이 같을 때만 `active` 초안의 `revision`을 증가시키고, 해당 초안의 기존 AI 심판 분석을 `stale`로 만든다. 사용자는 수정한 초안을 다시 `확인`해 새 분석을 요청한다.
- 자동 저장·버림·AI 심판 요청도 `expected_revision`이 현재 초안 버전과 같을 때만 처리한다. 일치하지 않으면 서버는 `draft_revision_conflict`를 반환하며, 오래된 기기의 자동 저장이나 AI 요청이 최신 초안을 덮어쓰거나 오래된 버전의 분석을 만들 수 없다.
- 전송된 개인 기록은 작성자만 삭제할 수 있다. 서버는 초안·연결된 AI 심판 결과를 함께 비공개 삭제 처리하고, 전송된 메시지를 수정하거나 삭제하지 않는다.
- `메시지 전송`은 반드시 준비된 AI 심판 분석 ID를 포함한다. 서버는 그 분석·초안의 요청자·방·입력 해시를 검증한다.
  - 분석의 `draft_revision`은 전송 시점 초안의 `revision`과 같아야 한다.
  - `original`은 전송 본문의 해시가 분석 입력 해시와 같아야 한다.
  - `recommendation`은 분석 결과에 들어 있는 추천 항목 중 하나여야 한다.
- 위 검증은 화면이 아니라 서버에서 수행한다. 서버는 AI 분석과 초안이 현재 전송 요청자의 것이고 같은 대국방에 속하는지, 분석이 현재 초안 버전에 대한 것인지, 전송할 본문이 분석받은 원문 또는 해당 분석의 추천 문장 중 하나인지 확인한다. 조건을 충족하지 않으면 전송을 거절한다. 따라서 사용자가 화면의 `확인` 절차를 건너뛰고 서버에 직접 전송을 요청해도, AI 분석을 거치지 않은 문장이나 분석 후 임의로 바꾼 문장은 전송할 수 없다.
- 검증을 통과해 전송이 성공하면 메시지 확정, 초안의 `sent` 전환, 메시지·분석 연결을 함께 기록한다. 이때 메시지만 방의 다음 `sequence`를 받아 실시간 전송되며, 비공개 초안과 AI 심판 결과는 상대에게 전송하지 않는다.



### 4.3 개인 형세 파악과 AI 문철

```text
형세 파악 요청 → private_position 분석 생성 → private 범위 결과 ready
AI 문철 신청 → room_review_request pending → 상대 수락
  → room_review 분석 생성·room 공용 pending → room 범위 결과 ready
                                               └→ result_type: normal 또는 restricted
```

- 개인 형세 파악과 AI 문철 신청은 요청 시점까지의 확정 메시지 순번을 `context_through_sequence`으로 남긴다. 늦게 도착한 메시지를 과거 분석에 섞지 않는다.
- 개인 형세 파악은 요청자 전용(`visibility: private`)이다. 결과·요청 여부·이벤트는 상대에게 보내지 않으며 작성자 본인의 다른 기기에서만 `private_revision`으로 복구한다.
- AI 문철 신청은 두 방 멤버에게 보인다. 신청자가 자신의 동의를 표시한 뒤 상대가 `pending` 신청을 수락해야만 서버가 `room_review` 분석을 만든다. 수락 전에는 AI 서비스 요청·분석 결과·자동 답변을 만들지 않는다.
- 수락 뒤 AI 문철은 대국방 공용(`visibility: room`)이며, 두 멤버 모두 같은 `pending` 로딩 상태와 `ready` 결과를 읽는다. 상태 변경과 결과는 `room_revision`을 증가시켜 두 화면에 동기화한다.
- 공용 AI 문철 분석이 최초 실패하면 해당 신청을 `failed`로 바꾸고, 분석 내용 없이 실패 사실을 두 멤버에게 공용으로 알린다. 신청자만 동일한 `context_through_sequence`과 이미 확정된 상대 수락을 유지한 채 한 번 다시 `processing`으로 재시도할 수 있다. 재시도 실패 또는 신청자 취소는 해당 신청을 `cancelled`로 바꾸며, 새 문철은 새 `pending` 신청과 상대 수락부터 시작한다.
- AI 문철의 `normal` 결과는 `shared_summary`(확정 메시지의 말·사건 요약), `different_points`(각자가 중요하게 말한 기준·요청의 차이), `inferred_hopes_and_worries`(`AI의 추정`인 바람과 걱정), `next_moves`(다음 대화 선택지)를 포함한다. `restricted` 결과에는 분석 본문을 만들지 않는다. 승패·잘잘못·관계 상태 판정은 저장하거나 표시하지 않는다.
- `ready`인 최신 문철은 대국방의 현재 문철로 연다. 이전 `room_review` 결과는 같은 방 멤버에게 읽기 전용 기록으로 제공한다. 새 문철은 최신 결과 아래에서 새 신청을 만들며, 새 신청의 `context_through_sequence`은 이후 확정 메시지를 기준으로 다시 잡는다.
- `processing` 동안에는 새 신청·현재 문철 열기 행동을 막는다. `ready` 전환은 두 멤버에게 준비 완료 알림을 보내지만 결과 화면을 자동으로 열지 않는다.
- 준비 완료 알림은 사용자가 현재 `room_review`를 열면 그 사용자에게만 확인 처리한다. 확인 처리된 사용자는 대국방의 `AI 문철 확인하기`로 재진입하며, 상대의 확인 여부·확인 시각은 공용 조회·이벤트에 포함하지 않는다.
- 종료 대국 기록의 `AI 문철 기록` 조회는 `room_review` 중 두 멤버 모두의 사용자 전용 확인 상태가 있는 `ready` 결과만 반환한다. 개인 `private_position`, `pending`·`processing`, 한 멤버만 확인한 `ready` 결과는 반환하지 않는다.



### 4.4 무승부 협상

```text
제안 버전 생성(제안자 자동 수락)
  → 상대가 조건 선택 후 수락 → agreed → 선택 조건 미션 생성
  → 조건 0개 제안의 상대 수락 → agreed → 미션 생성 없음
  → 상대 카운터오퍼 메시지 → 제안자 수정 → 새 제안 버전 생성
  → `open` 상태에서 어느 쪽이든 계속 대국 → cancelled
```

- 새 제안 버전이 현재 활성 버전이 된다. 이전 버전은 이력으로 남지만 수락·선택할 수 없다.
- 제안자는 AI 추천과 직접 입력으로 조건 선택지를 만들고 `single`(정확히 1개), `multiple`(1개 이상), `none`(조건 없음)을 정한다. 조건마다 책임 주체를 `나`·`상대`·`함께` 중에서 명시한다. AI 추천 조건의 기본 책임 주체는 제안자지만 수정 가능하다. 상대는 제안자의 선택지·책임 주체를 수정하거나 직접 추가할 수 없다.
- 상대가 활성 버전을 수락하려면 `single`·`multiple`에서는 선택 방식에 맞는 조건 선택을 함께 보낸다. `none`은 선택 없이 수락만 보낸다. 제안자는 생성과 동시에 수락한 상태이므로, 상대의 유효한 수락과 필요한 선택이 기록되면 즉시 `agreed`가 된다.
- `open` 활성 버전은 상대의 선택·수락·계속 대국·카운터오퍼 전까지 제안자도 변경하거나 재발송할 수 없다. 상대의 카운터오퍼는 메시지 하나를 남기고 활성 버전을 `counter_requested`로 바꾼다. `counter_requested`에서는 제안자만 이 메시지를 보고 조건·책임 주체·선택 방식을 수정해 다음 버전을 생성할 수 있고, 카운터오퍼를 보낸 상대는 기존 제안을 선택·수락하거나 추가 카운터오퍼를 만들 수 없다. 제안에는 기한이 없으며, 제안자는 바뀌지 않는다. 이전 선택·수락은 새 버전으로 넘어가지 않는다. 새 버전의 각 조건은 책임 주체를 명시하므로 이전 버전에서 추정해 이어받지 않는다.
- 카운터오퍼 메시지는 일반 `message`가 아니라 해당 `settlement_offer`에만 연결한다. 현재 대국방 조회는 최신 활성 상태만 반환하고, `무승부 협상 기록 보기` 조회는 현재 진행 중이거나 가장 최근에 종료된 협상 1건의 제안 버전·카운터오퍼·수락·계속 대국·합의 결과만 시간순 읽기 전용으로 반환한다. 새 협상을 시작하면 이전 협상은 이 조회의 대상에서 제외한다.
- `계속 대국`은 열린 협상 하나를 `cancelled`로 바꾸며, 어떤 미션도 만들지 않는다.
- 조건이 있는 합의와 선택 조건의 미션 생성은 하나의 성공/실패 단위다. `none` 합의는 미션을 만들지 않고 합의만 기록한다. 같은 합의에서 중복 미션이 생겨서는 안 된다.
- 합의가 확정되면 같은 성공/실패 단위로 방을 `closed`로 바꾸고 `closed_at`을 기록한다. 종료된 방은 지난 대국 목록에 보이며, 미션은 방 상태와 독립적으로 처리한다.



### 4.5 미션

```text
agreed → in_progress

개인: in_progress → completion_requested → 상대 confirm → completed
                                         └→ request_revision → revision_requested → 수행자 resume → in_progress
      in_progress 또는 revision_requested → 수행자 abandon → abandoned

공동: in_progress + 두 참여자의 joint_checkin → completed
      in_progress → 한 참여자 abandon → abandoned

수정: in_progress 또는 revision_requested → 수정 제안 open
      → 상대 accept → 새 미션 버전 적용 → in_progress
      → 상대 reject / 제안자 cancel → 기존 미션 유지
```

- `completion_requested`는 개인 미션의 상대 확인 대기 상태다. `counterpart_review`는 별도 저장 상태가 아니라 이 상태를 보여 주는 화면 단계다.
- 개인 미션은 `owner_user_id`만 완료 요청·재수행 시작·포기를 할 수 있고, 상대만 확인·재수행 요청을 할 수 있다. 재수행 시작 전까지는 `revision_requested`를 유지한다.
- 공동 퀘스트는 두 참여자가 현재 미션 버전에 각각 완료 체크인을 하면 자동 완료된다. 한 참여자가 포기하면 즉시 `abandoned`가 되며, 다른 참여자의 체크인만으로 완료될 수 없다.
- `in_progress` 또는 `revision_requested`인 미션은 방 멤버 누구나 문구·기한·개인 수행자·공동 참여자·개인/공동 유형의 수정 제안을 하나 만들 수 있다. 제안이 열려 있어도 기존 미션의 값·책임·상태는 그대로 유효하다.
- 수정 제안은 제안자가 아닌 상대만 수락 또는 거절할 수 있고, 제안자는 취소할 수 있다. 수락하면 서버는 제안 상태 변경, `mission_revision` 생성, `mission.current_revision` 증가, 새 필드 적용, 이전 완료 요청·공동 체크인 무효화를 하나의 성공/실패 단위로 처리하고 미션을 `in_progress`로 바꾼다. 거절·취소하면 기존 미션은 바꾸지 않는다.
- 수락 전 미션이 `completed`·`abandoned`가 되거나 현재 버전이 달라지면 수정 제안은 `stale`이 되어 적용할 수 없다. `completed`·`abandoned`·`completion_requested` 상태에서는 새 수정 제안을 만들 수 없다.

서버는 요청 종류에 따라 다음 내용을 확인한다.

- **방 안의 정보를 조회하거나 행동을 요청할 때:** 로그인한 사용자가 해당 방의 참여자로 등록되어 있는지 먼저 확인한다. 참여자가 아니면 메시지 조회·전송, 협상, 미션 처리 등 방 내부 기능을 허용하지 않는다. 참여자라면 위 권한 표에 따라 요청한 행동을 할 수 있는지도 확인한다.
- **새 방을 만들 때:** 로그인한 사용자인지, 이미 진행 중인 방이 있어 사용자당 한 개 제한에 걸리는지 확인한다. 아직 만들지 않은 방의 참여자일 것을 요구하지는 않는다.
- **미로그인 초대 링크를 열 때:** 초대 토큰을 검증하거나 초대 정보를 반환하지 않는다. 로그인·회원가입 화면만 제공하고, 인증 완료 뒤 원래 링크로 돌아갈 경로만 보존한다. 미로그인 상태에서는 초대 코드 입력 기능도 제공하지 않는다.
- **로그인 뒤 초대를 수락할 때:** 로그인한 사용자가 초대 링크를 다시 열거나 시작 화면에서 코드를 입력했는지, 해당 초대가 유효한지, 방에 입장할 빈자리가 있는지, 사용자가 이미 진행 중인 다른 방을 갖고 있지 않은지를 확인한다. 모두 통과할 때만 멤버 생성·초대 사용 처리·방 활성화를 하나의 성공/실패 단위로 처리한다. 초대 수락 전에는 아직 방 참여자가 아니므로, 기존 참여자인지를 입장 조건으로 요구하지 않는다.

사용자의 브라우저가 보낸 `user_id`(사용자 식별자), `public_member_key`, 역할, 방 상태, 수락 여부만으로 권한이나 처리 결과를 결정하지 않는다. 서버가 로그인 정보를 통해 확인한 사용자와 서버에 저장된 참여자·방·제안 상태를 기준으로 판단한다. 예를 들어 브라우저가 다른 사람의 `user_id` 또는 `public_member_key`를 보내거나 “상대도 수락했다”고 보내더라도, 서버가 확인한 사실과 다르면 그대로 처리하지 않는다.

## 6. 실시간 동기화 규칙



### 6.1 확정 순서

1. 클라이언트가 명령을 보낸다.
2. 서버가 인증 세션·권한·현재 상태를 검증한다.
3. 서버가 데이터를 확정 저장한다. 방 공용 변경에는 `room_revision`을, 작성자 전용 변경에는 `private_revision`을 각각 증가시키며, 한 명령이 둘 다 바꾸면 둘 다 같은 성공/실패 단위로 기록한다.
4. 저장 성공 뒤에만 수신 범위에 맞는 실시간 이벤트를 보낸다.

실시간 연결은 알림 수단이며, 데이터의 기준은 서버에 저장된 상태다. 이벤트를 놓치거나 순서가 뒤바뀐 클라이언트는 마지막으로 적용한 `room_revision` 이후 공용 변경과 `private_revision` 이후 본인 비공개 변경을 각각 다시 조회해 복구한다. 연결 회복 뒤 자동 복구는 최대 30초 동안만 시도한다. 그 뒤에도 실패하면 마지막 확정 상태를 읽기 전용으로 유지하고 사용자의 수동 재시도 또는 메인 복귀를 기다린다. 자동 재시도 횟수·간격과 전송 기술은 M1.3에서 정한다.

### 6.2 최소 이벤트 목록


| 이벤트                                          | 수신자           | 확정 데이터                                           |
| -------------------------------------------- | ------------- | ------------------------------------------------ |
| `room.member_joined`                         | 방 멤버          | 입장한 `public_member_key`, `room_display_name`, 화면용 `member_label`, 방 활성 상태 |

| `draft.updated`                              | 초안 작성자        | `private_revision`과 확정된 초안 `revision`이 포함된 변경 알림; 본문은 작성자 인증 조회로만 가져옴 |

| `message.sent`                               | 방 멤버          | 메시지, 발신자의 `public_member_key`, 순번, 시각                |
| `room_review.requested` / `room_review.accepted` | 방 멤버 | 신청자·상대의 방 전용 공개 키, 기준 메시지 순번, 신청·수락 상태. 수락 뒤 두 화면은 공용 로딩을 표시한다. |
| `room_review.failed` | 방 멤버 | 분석 내용 없이 동일 신청의 실패 상태와 신청자 재시도 가능 여부. |
| `analysis.ready`                             | 분석 가시 범위의 사용자 | AI 심판·개인 형세 파악은 요청자 전용 `private_revision`, 상대 수락 뒤 생성한 AI 문철은 방 공용 `room_revision`과 준비 완료 알림을 포함한다. 화면은 결과를 자동으로 열지 않는다. |
| `settlement.offer_changed`                   | 방 멤버          | 현재 제안 버전, 제안자·조건 책임 주체의 `public_member_key`, 조건, 수락 현황, 읽기 전용 또는 카운터오퍼 수신 상태 |
| `settlement.agreed` / `settlement.cancelled` | 방 멤버          | 협상 최종 상태                                         |
| `mission.created` / `mission.updated`        | 방 멤버          | 현재 버전, 수행자·확인자의 `public_member_key`, 미션·수행 기록·상태 |
| `mission.change_offer_changed`               | 방 멤버          | 수정 제안의 제안자 `public_member_key`, 기준 버전, 제안 값, `open`·수락·거절·취소·만료 상태 |


- 방 공용 이벤트에는 `room_id`, `room_revision`, 발생 시각을 넣는다. 작성자 전용 이벤트에는 `room_id`, `private_revision`, 발생 시각을 넣는다. 클라이언트는 각 흐름에서 더 오래된 순번을 적용하지 않는다.
- 방 상태 조회는 두 참가자의 `public_member_key`, `room_display_name`, `member_label`을 포함한다. 클라이언트는 공용 이벤트의 참가자 키를 이 목록으로 해석한다. `member_label`은 이름이 다르면 이름만, 같으면 `이름 · A/B`다.
- AI 심판과 개인 형세 파악의 초안·입력 해시·결과·요청 여부는 상대에게 이벤트로 보내지 않는다.
- AI 심판·개인 형세 파악 실패는 방 상태를 바꾸지 않고 요청자에게만 재시도 가능한 오류를 전달하며, 분석 성공 전 메시지 전송은 허용하지 않는다. 공용 AI 문철 실패는 `room_review.failed`로 두 멤버에게만 알리고, 신청자만 같은 요청을 재시도할 수 있다.
- 비공개 변경 조회에서 순번이 끊기거나 변경 목록 보관 기간을 지났으면, 서버는 요청자에게만 작성 중 초안·현재 AI 심판 상태·삭제 표식의 최신 스냅샷을 반환한다. 삭제 표식이 있는 본문·AI 결과는 반환하지 않는다.
- `draft.updated`를 받은 기기에 미저장 입력이 있으면 이벤트만으로 작성창 본문을 바꾸지 않는다. 최신 초안을 조회한 뒤 `draft_revision_conflict`와 같은 충돌 해결 선택지를 표시하며, 이 정보는 작성자 외 누구에게도 보내지 않는다.

| A가 로그인 후 방 생성   | 사용자 A, 인증 수단, 방(`waiting`), 멤버 A, 활성 초대     | A에게 초대 코드·링크와 상대 대기 상태 |
| B가 로그인 후 초대로 입장 | 사용자 B, 인증 수단, 멤버 B, 초대(`used`), 방(`active`) | 양쪽에 상대 표시 이름과 입장 상태    |
| A가 날선 초안 확인     | A의 비공개 AI 심판 분석                             | A에게만 심판 결과 또는 제한 안내    |
| A가 원문/추천 전송     | 순번이 있는 메시지                                  | 양쪽에 같은 메시지 순서          |
| A가 개인 형세 파악 요청 | A의 비공개 `private_position` 분석 | A에게만 형세·쟁점·다음 판단 표시 |
| A가 AI 문철 신청        | `room_review_request(pending)` | B에게 수락 안내, A에게 상대 수락 대기 |
| B가 AI 문철 수락        | 신청 `accepted`, 방 공용 `room_review` 분석 | 양쪽에 공용 로딩 뒤 대화 요약·서로 다른 지점·AI의 추정·다음 수 표시 |
| A가 조건부 무승부 제안   | 열린 협상, 제안 버전 1, 조건 선택지, 선택 방식, A 수락                    | 양쪽 상단에 제안과 선택 방식     |
| B가 카운터오퍼        | 카운터오퍼 메시지, 제안 버전 1의 `counter_requested` 상태                      | 양쪽에 B의 요청 메시지와 A의 수정 대기 상태  |
| A가 수정 후 재제안     | 제안 버전 2, A 수락, 이전 선택·수락 초기화             | 양쪽에 새 선택지와 선택 방식              |
| B가 선택 후 수락           | 협상(`agreed`), 방(`closed`), B의 조건 선택, 선택 조건별 미션, 수행 기록 시작점             | 메인의 미션·지난 대국 목록              |
| 수행·상호 확인        | 미션 행동과 상태 변경                                | 양쪽에 완료 요청·확인·완료 상태     |

## 8. M1.2와 M1.3으로 넘길 확인 항목



### M1.2 인터페이스·계약

- 추천 문구 선택, 카운터오퍼 조건의 개인/공동 유형 선택을 화면에서 어떻게 노출할지
- 상태 조회, 명령 요청, 이벤트의 정확한 요청·응답 필드와 오류 문구
- AI 로딩·실패·`restricted`와 실시간 재연결 화면 상태



### M1.3 기술 선택

- 카카오·구글 OAuth 연동, 이메일·비밀번호 가입·검증·재설정, 인증 세션의 발급·보관·만료와 방 접근 검증 구현 방식
- 데이터 저장소의 트랜잭션·순번 생성·이벤트 재조회 방식
- 실시간 전송 수단과 접속 상태 처리 방식
- AI 모델·프롬프트 기반 `restricted` 분류·대화 맥락 길이
- 대화·분석의 보관 기간과 삭제 정책

이 초안은 위 선택이 정해져도 변하지 않아야 하는 제품 규칙(두 명 제한, 필수 AI 훈수, 양측 합의 전 미션 없음, 대국방 밖 비공개)을 우선 고정한다.
