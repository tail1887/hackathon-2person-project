# 커플들이 집착하는 AI 심판이 되었다 — M1.1 시스템·데이터 정의

> **상태: 초안 · 2026-09-17**
>
> 이 문서는 [MVP 명세](1_MVP_명세.md)의 고정 데모 시나리오를 구현하기 위한 논리 시스템·데이터 계약이다. DB, 실시간 전송 수단, AI 제공사 같은 기술 선택은 M1.3에서 결정한다.

## 1. 범위와 시스템 경계

### 1.1 M1.1이 다루는 것

- 로그인 계정 두 명의 대국방 연결과 미션 재진입
- 메시지, AI 심판, AI 문철, 무승부 협상, 미션의 저장 단위와 상태
- 대국방 멤버만 데이터를 읽고 바꾸게 하는 권한 규칙
- 두 브라우저가 같은 순서의 확정 데이터를 보게 하는 실시간 동기화 규칙

### 1.2 이번 단계에서 선택하지 않는 것

- 프런트엔드·백엔드·DB·인증·실시간·AI·배포 제품과 라이브러리
- 사진 파일 저장소와 AI 이미지 판별 방식(사진 인증은 선택 데모 기능)
- 장기 보관, 계정 복구, 탈퇴·삭제의 운영 정책

### 1.3 논리 구성

```text
두 브라우저
  │ 명령 요청 / 상태 조회
  ▼
애플리케이션 서버 ── AI 분석 요청 ── AI 서비스
  │ 검증 후 확정 데이터 기록
  ├── 영속 데이터 저장소
  └── 실시간 이벤트 전송 ── 대국방의 두 브라우저
```

- 서버가 메시지·협상·미션의 유일한 확정 주체다. 클라이언트의 임시 입력이나 화면 상태는 사실로 취급하지 않는다.
- AI는 필요한 대화 맥락과 입력만 받아 분석 결과를 돌려준다. AI 결과는 약속·합의·미션을 스스로 확정할 수 없다.
- 기술 선택 전에는 `명령 요청`, `상태 조회`, `실시간 이벤트`라는 논리 경계만 사용한다. 구체 API와 이벤트 형식은 M1.2에서 정한다.

## 2. 식별과 접근 모델



### 2.1 로그인 계정 사용자

대국방 생성과 초대 수락은 로그인한 `사용자`만 할 수 있다. 사용자는 카카오·구글·네이버 간편 로그인 또는 이메일·비밀번호 회원가입으로 계정을 만든다. 화면과 실시간 이벤트에는 내부 `id`가 아닌 표시 이름만 노출한다.

계정에 연결된 인증 세션은 기술 구현과 무관하게 다음 권한 판단에 필요하다.

- 방을 만든 사람은 `creator`, 초대로 입장한 사람은 `invitee` 역할을 가진다.
- 역할보다 **대국방 멤버인지 여부**가 기본 접근 조건이다. 두 역할의 메시지·협상·미션 권한은 동등하다.
- 한 로그인 계정은 진행 중인 대국방을 하나만 가진다. 새 방 생성과 초대 입장 시점에 이 조건을 다시 확인하며, 제한을 넘으면 아무 상태도 바꾸지 않고 거절한다.
- 사용자는 같은 계정으로 다시 로그인해 진행 중인 방과 미션에 재진입한다. 브라우저를 바꾸거나 세션이 만료되어도 계정 인증 뒤 권한이 복구된다.
- 외부 제공자의 식별자와 이메일·비밀번호 인증 정보는 대국방 상대에게 노출하지 않는다.



### 2.2 초대

방 생성 시 한 개의 `초대`를 만들고, 공유 링크용 비밀 토큰과 사람이 입력할 6자리 코드를 함께 발급한다. 둘은 같은 초대를 가리킨다. 로그인하지 않은 사용자가 링크를 열면 인증을 마친 뒤 원래 초대를 계속 수락할 수 있어야 한다.

- 링크 토큰은 충분히 추측하기 어렵게 생성하고 저장 시에는 원문 대신 검증 가능한 값만 보관한다.
- 6자리 코드는 활성 초대 안에서 충돌하지 않아야 하며, 충돌 시 다시 생성한다.
- 초대 수락은 초대가 활성 상태이고 방의 두 번째 자리가 비어 있을 때만 성공한다. 성공하면 초대는 `사용됨`이 되고 추가 입장은 모두 거절한다.
- 미로그인 링크 방문은 토큰 검증 뒤 짧은 수명의 `pending_invite` 맥락을 보존한다. 이메일·비밀번호 회원가입 성공 시에는 인증 세션을 즉시 만들고, 간편 로그인 성공 시에도 같은 맥락을 인증 세션에 연결한다.
- 인증 완료 뒤 서버는 초대 상태·빈자리·진행 중인 방 제한을 다시 확인한다. 모두 통과하면 초대받은 사용자를 방 멤버로 추가하고, 초대를 `사용됨`으로 바꾸고, 방을 `진행 중`으로 바꾼 뒤 대국방으로 이동시킨다. 셋 중 하나라도 처리할 수 없으면 세 상태를 모두 이전 그대로 두고 방으로 이동시키지 않으며, 실패 원인을 안내한다.

### 3.1 작성자 개인 기록

작성자 개인 기록은 `message_draft`와 그 초안에 연결된 `message_mediation` AI 분석이다. 다른 사용자·방 공용 이벤트·공용 복기에는 포함하지 않는다.

- **작성 중 초안:** 내용이 있는 초안만 자동 저장해 같은 계정의 다른 기기에서도 이어 쓴다. 빈 작성창은 기록하지 않는다. 초안 본문은 작성자만 읽는다.
- **전송 뒤 기록:** 메시지를 전송하면 초안 상태는 `sent`가 된다. 원문 초안·AI 심판 결과를 전송 메시지에 연결해 보관하고, 작성자만 `내 초안과 AI 심판 보기`에서 펼친다.
- **전송 전 버림:** 사용자가 초안을 명시적으로 버리면 `discarded`가 되어 더 이상 열람하지 않는다.
- **전송 뒤 개인 기록 삭제:** 작성자가 개인 기록 삭제를 선택하면 초안 본문·AI 심판 결과를 비공개 저장값과 작성자 화면·이후 개인 복기에서 즉시 제거한다. 여러 기기에 삭제 상태를 동기화하기 위한 `private_record_deleted_at`만 남기며, 이 값에는 삭제한 내용이 들어 있지 않고 복기에 쓰이지 않는다. 전송된 메시지 본문·방 공용 순번·협상·미션은 바꾸지 않는다. 실제 보관·완전 삭제 기간은 M1.3에서 정한다.
- **AI 분석 연결:** AI 심판 분석은 원문을 중복 저장하지 않고 `draft_id`와 `input_hash`로 해당 초안을 연결한다. 추천 문구와 안전 안내는 `result`에 저장해 작성자가 나중에 확인할 수 있게 한다.



### 3.2 서버 임시 처리 정보

아래 정보는 사용자 기능을 처리하는 동안만 쓰며, 대화 기록·개인 복기·공용 복기의 데이터가 아니다.

- **AI 요청 조합:** 서버는 AI 심판 요청 때 최신 초안, 필요한 최근 메시지, 안전 지침을 잠시 묶어 AI 서비스에 보낸다. 이 요청 조합 자체는 별도 기록으로 저장하지 않는다. 완료 뒤 남기는 것은 3.1의 AI 분석 결과뿐이다.
- **접속 상태:** 상대의 온라인·오프라인 표시에 쓰는 일시 상태다. 메시지·협상·미션의 사실이나 대화 기록으로 보관하지 않는다.
- **`pending_invite`:** 미로그인 사용자가 초대 링크를 열 때 링크 토큰을 검증한 뒤, 인증이 끝날 때까지 유지하는 짧은 수명의 초대 입장 맥락이다. 검증된 초대 ID와 만료 시각만 보관하며 원본 링크 토큰은 다시 저장하지 않는다. 로그인·회원가입 성공 뒤 초대를 다시 검증해 방에 입장시키고, 입장 성공·실패·만료 시 이 맥락은 폐기한다.

## 4. 상태 전이와 명령 규칙



### 4.1 대국방과 초대

```text
방 생성 → waiting + active 초대
상대가 유효한 링크/코드를 수락 → active + 초대 used
```

- `waiting` 방에서는 생성자만 입장해 있고, 초대 상태만 볼 수 있다. 메시지·AI 문철·협상은 `active` 뒤에 가능하다.
초대 수락이 성공하려면 다음 세 변경이 모두 함께 적용돼야 한다.

1. 초대받은 사용자를 방 멤버로 추가한다.
2. 해당 초대를 `사용됨`으로 바꾼다.
3. 방 상태를 `상대 대기`에서 `진행 중`으로 바꾼다.

방이 이미 찼거나 중간에 오류가 나면 세 변경을 하나도 적용하지 않는다. 즉, 사용자가 멤버로만 추가되거나 초대 코드만 소모되는 상태는 만들지 않는다.

### 4.2 AI 심판과 메시지

```text
초안 작성 → AI 심판 요청 → 분석 pending → ready
  ├→ result_type: normal 또는 safety_guidance
  ├→ 초안 수정 → 분석 stale → 다시 AI 심판 요청
  └→ 원문 전송 / 추천 문구 전송 → 메시지 확정
```

- `AI 심판 요청`은 요청자의 저장된 초안과 최근 확정 메시지 맥락을 사용한다. 결과의 `visibility`는 항상 `private`다.
- 분석이 `ready`여도 `result_type`이 `safety_guidance`일 수 있다. 이 경우 AI 심판 시트는 닫히지 않지만, 일반 추천은 제공하지 않고 안전 안내와 대국 중단 선택지를 보인다.
- `초안 수정`은 `active` 초안의 `revision`을 증가시키고, 해당 초안의 기존 AI 심판 분석을 `stale`로 만든다. 사용자는 수정한 초안을 다시 `확인`해 새 분석을 요청한다.
- 전송된 개인 기록은 작성자만 삭제할 수 있다. 서버는 초안·연결된 AI 심판 결과를 함께 비공개 삭제 처리하고, 전송된 메시지를 수정하거나 삭제하지 않는다.
- `메시지 전송`은 반드시 준비된 AI 심판 분석 ID를 포함한다. 서버는 그 분석·초안의 요청자·방·입력 해시를 검증한다.
  - 분석의 `draft_revision`은 전송 시점 초안의 `revision`과 같아야 한다.
  - `original`은 전송 본문의 해시가 분석 입력 해시와 같아야 한다.
  - `recommendation`은 분석 결과에 들어 있는 추천 항목 중 하나여야 한다.
- 위 검증은 화면이 아니라 서버에서 수행한다. 서버는 AI 분석과 초안이 현재 전송 요청자의 것이고 같은 대국방에 속하는지, 분석이 현재 초안 버전에 대한 것인지, 전송할 본문이 분석받은 원문 또는 해당 분석의 추천 문장 중 하나인지 확인한다. 조건을 충족하지 않으면 전송을 거절한다. 따라서 사용자가 화면의 `확인` 절차를 건너뛰고 서버에 직접 전송을 요청해도, AI 분석을 거치지 않은 문장이나 분석 후 임의로 바꾼 문장은 전송할 수 없다.
- 검증을 통과해 전송이 성공하면 메시지 확정, 초안의 `sent` 전환, 메시지·분석 연결을 함께 기록한다. 이때 메시지만 방의 다음 `sequence`를 받아 실시간 전송되며, 비공개 초안과 AI 심판 결과는 상대에게 전송하지 않는다.



### 4.3 AI 문철

```text
형세 파악 요청 → position 분석 생성 → room 범위 결과 ready
                                     └→ result_type: normal 또는 safety_guidance
```

- 문철은 요청 시점까지의 확정 메시지 순번을 `context_through_sequence`으로 남긴다. 늦게 도착한 메시지를 과거 분석에 섞지 않는다.
- 결과는 대국방 공용(`visibility: room`)이며, 두 멤버 모두 읽을 수 있다.
- 결과에는 `AI의 추정` 표기를 적용해야 하는 감정·의도 해석과 안전 상태를 구조화해 저장한다. 승패·잘잘못 판정은 저장하거나 표시하지 않는다.



### 4.4 무승부 협상

```text
제안 버전 생성(제안자 자동 수락)
  → 상대 수락 → agreed → 미션 생성
  → 상대 카운터오퍼 → 새 제안 버전 생성
  → 어느 쪽이든 계속 대국 → cancelled
```

- 새 제안 버전이 현재 활성 버전이 된다. 이전 버전은 이력으로 남지만 수락할 수 없다.
- 상대가 활성 버전을 수락하면 두 멤버의 ID가 `accepted_by_user_ids`에 모이고 즉시 `agreed`가 된다.
- 카운터오퍼를 한 사람은 새 조건에 자동 수락한 것으로 본다. 이전 제안의 수락은 새 버전으로 넘어가지 않는다.
- `계속 대국`은 열린 협상 하나를 `cancelled`로 바꾸며, 어떤 미션도 만들지 않는다.
- 합의와 미션 생성은 하나의 성공/실패 단위다. 같은 합의에서 중복 미션이 생겨서는 안 된다.



### 4.5 미션

```text
agreed → in_progress
개인: 수행자 완료 요청 → counterpart_review → 상대 confirm → completed
                                     └→ request_revision → revision_requested → in_progress
공동: 두 참여자 joint_checkin → completed
```

- 개인 미션은 `owner_user_id`만 완료 요청·포기를 할 수 있고, 상대만 확인·다시 요청할 수 있다.
- 공동 퀘스트는 두 참여자가 각각 완료 체크인을 하면 자동 완료된다. 개인 미션처럼 한 사람이 상대의 완료를 대신 처리할 수 없다.
- 사진 첨부가 구현되면 완료 요청에 선택적으로 붙인다. 사진의 AI 판별은 MVP 기본 완료 조건이 아니며, 상대 확인이 최종 기준이다.

## 6. 실시간 동기화 규칙



### 6.1 확정 순서

1. 클라이언트가 명령을 보낸다.
2. 서버가 인증 세션·권한·현재 상태를 검증한다.
3. 서버가 데이터를 확정 저장하고 방 단위 변경 순번(`room_revision`)을 증가시킨다.
4. 저장 성공 뒤에만 요청자 응답과 대국방 멤버 대상 실시간 이벤트를 보낸다.

실시간 연결은 알림 수단이며, 데이터의 기준은 서버에 저장된 방 상태다. 이벤트를 놓치거나 순서가 뒤바뀐 클라이언트는 마지막으로 적용한 `room_revision` 이후 변경을 다시 조회해 복구한다.

### 6.2 최소 이벤트 목록


| 이벤트                                          | 수신자           | 확정 데이터                                           |
| -------------------------------------------- | ------------- | ------------------------------------------------ |
| `room.member_joined`                         | 방 멤버          | 입장한 표시 이름, 방 활성 상태                               |
| `room.presence_changed`                      | 방 멤버          | 온라인/오프라인 표시용 상태; 영속 사실 아님                        |
| `draft.updated`                              | 초안 작성자        | 다른 기기 이어쓰기를 위한 초안 상태·수정 시각; 본문은 작성자에게만 전송 |
| `private_record.deleted`                     | 초안 작성자        | 전송 후 비공개 초안·AI 심판 기록 삭제 상태; 상대에게 전송하지 않음         |
| `message.sent`                               | 방 멤버          | 메시지, 발신자 표시 이름, 순번, 시각                           |
| `analysis.ready`                             | 분석 가시 범위의 사용자 | 분석 요약·상태. AI 심판은 요청자에게만, 문철은 방 전체에 전송            |
| `settlement.offer_changed`                   | 방 멤버          | 현재 제안 버전, 조건, 수락 현황, 기한                          |
| `settlement.agreed` / `settlement.cancelled` | 방 멤버          | 협상 최종 상태                                         |
| `mission.created` / `mission.updated`        | 방 멤버          | 미션·수행 기록·상태                                      |


- 모든 이벤트에는 `room_id`, `room_revision`, 발생 시각을 넣는다. 클라이언트는 더 오래된 순번을 적용하지 않는다.
- AI 심판의 초안, 입력 해시, 전송 뒤 보관된 심판 결과는 상대에게 이벤트로 보내지 않는다.
- AI 실패는 방 상태를 바꾸지 않는다. 요청자에게 재시도 가능한 오류만 전달하며, 분석 성공 전 메시지 전송은 허용하지 않는다.

- 추천 문구 선택, 카운터오퍼 조건의 개인/공동 유형 선택을 화면에서 어떻게 노출할지
- 상태 조회, 명령 요청, 이벤트의 정확한 요청·응답 필드와 오류 문구
- AI 로딩·실패·안전 안내와 실시간 재연결 화면 상태



### M1.3 기술 선택

- 카카오·구글·네이버 OAuth 연동, 이메일·비밀번호 가입·검증·재설정, 인증 세션의 발급·보관·만료와 방 접근 검증 구현 방식
- 데이터 저장소의 트랜잭션·순번 생성·이벤트 재조회 방식
- 실시간 전송 수단과 접속 상태 처리 방식
- AI 모델·안전 분류·대화 맥락 길이, 파일 저장소와 사진 접근 제어
- 대화·분석·사진의 보관 기간과 삭제 정책

이 초안은 위 선택이 정해져도 변하지 않아야 하는 제품 규칙(두 명 제한, 필수 AI 훈수, 양측 합의 전 미션 없음, 대국방 밖 비공개)을 우선 고정한다.
