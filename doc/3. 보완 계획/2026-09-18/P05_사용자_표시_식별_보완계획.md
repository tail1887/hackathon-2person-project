# P05 사용자 표시·식별 보완계획

> 상태: 확정 · 시스템·데이터 정의 반영 완료 · 2026-09-18

## 1. 목적과 범위

이 문서는 [M1.1 검증보고서 v2의 P05](../../2.%20검증보고서/M1.1_검증보고서_v2.md)인 **이름 공개·사용자 구분** 문제의 원인과 보완 방향을 정리한다.

대상은 대국방 안에서 상대에게 보여 주는 표시 이름, 메시지 발신자, 무승부 조건의 제안자·수행자, 미션의 수행자·확인자를 구분하는 규칙이다. 이메일, 간편 로그인 제공자 정보, 내부 `user.id` 같은 계정 식별 정보는 이 계획의 공개 대상이 아니다.

## 2. 현재 문제 분석

현재 시스템·데이터 정의는 화면과 실시간 이벤트에 내부 ID 대신 표시 이름만 노출한다고 설명한다. 반면 권한 표에서는 표시 이름 읽기를 로그인한 본인으로 제한해, 방 상대가 무엇을 읽을 수 있는지와 충돌한다.

표시 이름은 가입 또는 프로필에서 설정할 수 있으므로, 서로 다른 두 사용자가 같은 이름을 쓸 수 있다. 이 경우 메시지 발신자와 미션 수행자가 모두 `민지`처럼 표시되면 다음을 판별할 수 없다.

| 사례 | 현재 규칙의 공백 | 사용자 영향 |
| --- | --- | --- |
| 두 사용자가 모두 `민지`를 표시 이름으로 사용 | 이벤트에 표시 이름만 있다. | 누가 메시지를 보냈는지 알기 어렵다. |
| `민지`에게 개인 미션을 배정 | 조건·미션의 수행자 표기가 중복된다. | 누가 완료 요청 또는 포기를 할 수 있는지 혼란스럽다. |
| 한 사용자가 프로필 표시 이름을 변경 | 기존 방 기록에서 과거 발신자를 어떻게 보일지 정의돼 있지 않다. | 같은 사람이 다른 사람처럼 보이거나 과거 기록의 맥락이 흐려질 수 있다. |
| 권한 확인 또는 실시간 재연결 | 서버는 내부 ID를 쓰지만 클라이언트가 구분할 공개 기준이 없다. | 안전한 권한 확인과 이해 가능한 화면 표시를 함께 검증하기 어렵다. |

## 3. 보완 목표와 원칙

1. 방 참가자는 상대의 표시 이름을 읽을 수 있어야 한다.
2. 같은 표시 이름이어도 방 안의 모든 발신자·수행자·확인자를 구분할 수 있어야 한다.
3. 내부 `user.id`, 이메일, 인증 제공자 정보는 화면·공용 이벤트·초대 링크에 노출하지 않는다.
4. 사용자 식별은 방 범위로 한정해, 한 방에서의 표기가 다른 방의 계정 추적 수단이 되지 않게 한다.
5. 표시 이름을 바꾸더라도 이미 생성된 방의 대화·미션 기록에서 참가자 구분이 바뀌지 않아야 한다.

## 4. 확정 보완안

### 4.1 방 전용 공개 식별 키와 이름 스냅샷

각 `room_member`에 서버가 생성하는 방 전용 `public_member_key`와 입장 시점의 `room_display_name`을 둔다.

| 항목 | 의미 | 공개 범위 |
| --- | --- | --- |
| `user_id` | 서버가 권한 검사에 쓰는 내부 계정 식별자 | 서버만 사용 |
| `public_member_key` | 해당 방에서만 유효한 참가자 키. 예: `A`, `B` 또는 난수 기반 짧은 키 | 그 방의 두 참가자에게만 반환 |
| `room_display_name` | 방 입장 시 계정 표시 이름을 복사한 값 | 그 방의 두 참가자에게만 표시 |
| `member_label` | 화면용 표기. 이름이 겹치면 `민지 · A`처럼 키를 덧붙인 값 | 그 방의 두 참가자에게만 표시 |

`public_member_key`는 계정의 내부 ID나 전역 사용자명으로 사용하지 않는다. 방마다 새로 생성하고, 다른 방의 참가자 목록·이벤트·검색 결과에는 재사용하지 않는다.

### 4.2 이름 충돌 표기

두 `room_display_name`이 다르면 평소에는 이름만 `member_label`로 표시한다. 이름이 같을 때만 두 참가자 모두에게 키를 붙인다.

```text
이름이 다름:  민지, 준호
이름이 같음:  민지 · A, 민지 · B
```

이 규칙을 메시지 헤더, 무승부 조건의 제안자·책임 주체, 미션의 수행자·확인자, 활동 기록에 동일하게 적용한다. `나`처럼 현재 사용자를 가리키는 화면 문구는 유지할 수 있지만, 과거 기록과 상대가 보는 화면에는 `member_label`을 함께 쓴다.

### 4.3 데이터 조회와 실시간 이벤트

방 조회 응답은 참가자 목록의 `public_member_key`, `room_display_name`, `member_label`을 포함한다. 메시지·협상·미션 이벤트는 내부 `user_id` 대신 행위자의 `public_member_key`를 포함하고, 클라이언트는 참가자 목록으로 화면 표기를 해석한다.

서버의 권한 검사는 계속 `user_id`와 `room_member` 관계로 수행한다. 클라이언트가 보낸 `public_member_key`만으로 권한을 부여하지 않는다.

### 4.4 프로필 이름 변경

프로필의 표시 이름을 바꿔도 기존 방의 `room_display_name`과 `member_label`은 바꾸지 않는다. 새로 만드는 방 또는 새로 입장하는 방부터 새 표시 이름을 복사한다. 이로써 기존 메시지와 미션의 참가자 표기가 변하지 않는다.

## 5. 대안과 권장 이유

| 안 | 방식 | 장점 | 한계 |
| --- | --- | --- | --- |
| A | 가입 단계에서 전역 고유 표시 이름을 강제 | 화면 표기가 단순하다. | 커플 대화에 불필요한 사용자명 경쟁이 생기며, 프로필 이름 변경도 제한된다. |
| B | 표시 이름 뒤에 내부 ID 일부를 항상 노출 | 구현 범위가 작다. | 내부 식별자 노출 위험과 낯선 화면 표기가 생긴다. |
| C | 방 전용 키·이름 스냅샷을 두고, 이름 충돌 때만 보조 표기 | 같은 이름을 구분하면서 계정·방 밖 추적을 피하고 기록도 안정적이다. | `room_member` 필드와 이벤트 계약을 추가해야 한다. |

MVP에는 **C안**을 적용한다. 두 사람만 있는 방에서도 같은 이름은 충분히 발생할 수 있고, 메시지·미션 책임이 핵심인 제품이므로 구분 규칙이 필요하다. 반면 전역 고유 사용자명이나 내부 ID 노출은 문제 해결 범위를 넘는다.

## 6. 재검증 시나리오와 완료 기준

| 시나리오 | 기대 결과 |
| --- | --- |
| A와 B가 모두 `민지`로 방에 입장 | 두 사람의 화면에서 참가자·메시지·미션 표기가 각각 `민지 · A`, `민지 · B`로 구분된다. |
| A가 메시지와 조건을 만들고, B가 미션을 완료 요청 | 모든 이벤트가 행위자의 `public_member_key`로 연결되고, 화면에서 발신자·제안자·수행자를 혼동하지 않는다. |
| A만 표시 이름을 `민지`에서 `민아`로 변경 | 기존 방의 과거 메시지·미션 표기는 바뀌지 않고, 새 방부터 `민아`가 표시된다. |
| B가 재접속해 방 상태와 이벤트를 다시 조회 | 참가자 목록을 기준으로 같은 이름의 과거·신규 이벤트를 같은 사람에게 연결한다. |
| 방 밖 사용자가 참가자 정보를 조회하려고 시도 | 방 전용 키·표시 이름을 포함한 참가자 목록과 이벤트를 받지 못한다. |

다음 조건을 모두 만족하면 P05를 문서상 해소로 바꾼다.

- 상대가 볼 수 있는 표시 이름의 읽기 권한과 범위가 권한 표·이벤트 규칙에 일치한다.
- `room_member`의 방 전용 공개 식별 키와 이름 스냅샷이 정의돼 있다.
- 모든 공용 행위가 내부 `user_id`가 아닌 방 전용 키로 참가자와 연결된다.
- 동일 이름·이름 변경·재접속·방 밖 접근 사례의 기대 결과가 정의돼 있다.

## 7. 후속 구현에서 정할 항목

- `public_member_key`를 단순 `A`·`B`로 보일지, 난수 기반 키를 서버에서만 보관하고 화면에는 `A`·`B` 별칭으로 보일지
- 이름 충돌이 해소된 뒤에도 기존 방의 보조 표기를 유지할지에 대한 화면 세부 규칙
- 입장 취소·재초대·탈퇴 뒤 같은 계정이 다시 입장할 때 기존 키를 재사용할지 여부
- M1.2 인터페이스 계약에서 참가자 목록, 공용 이벤트, 미션 조회의 정확한 필드명
