# P04 비공개 이벤트 재동기화 보완계획

> 상태: 확정 · 시스템·데이터 정의 반영 완료 · 2026-09-18

## 1. 목적과 범위

이 문서는 [M1.1 검증보고서 v2의 P04](../../2.%20검증보고서/M1.1_검증보고서_v2.md)인 **비공개 이벤트 복구** 문제의 원인과 보완 계획을 정리한다.

대상은 같은 사용자가 여러 기기에서 사용하는 다음 작성자 전용 데이터다.

- 작성 중 초안의 저장·수정·버림
- AI 심판 요청 결과의 준비·무효화·제한됨 상태
- 전송 뒤 개인 기록의 삭제

방 공용 메시지·협상·미션의 재동기화는 기존 `room_revision` 규칙의 범위이며, 이 문서에서 바꾸지 않는다. 여러 기기의 동시 초안 수정 충돌은 별도 쟁점인 R02다.

## 2. 현재 문제 분석

현재 시스템은 방 공용 변경에 `room_revision`을 부여하고, 재접속한 클라이언트가 마지막 순번 뒤의 변경을 다시 조회하도록 정의한다. 그러나 초안·AI 심판·개인 기록 삭제는 작성자에게만 보이는 이벤트다.

따라서 현재 규칙만으로는 다음 질문에 답할 수 없다.

- 작성자의 다른 기기가 초안 저장 이벤트를 놓쳤을 때, 어느 비공개 변경부터 다시 받아야 하는가?
- 방 공용 순번이 증가했을 때, 그 사이에 작성자 전용 변경이 있었는지 어떻게 구분하는가?
- 전송 뒤 개인 기록 삭제 이벤트를 놓친 기기가 이전 초안·AI 심판 결과를 다시 표시하지 않게 하려면 무엇을 확인해야 하는가?

| 사례 | 현재 규칙의 공백 | 사용자 영향 |
| --- | --- | --- |
| 기기 A가 초안을 수정하고 기기 B가 오프라인 | `draft.updated`는 B가 놓칠 수 있지만 B의 마지막 비공개 순번이 없다. | B가 오래된 초안을 계속 보여 주거나, 최신 초안을 알 수 없다. |
| AI 심판 결과가 작성자에게만 도착 | `analysis.ready`는 상대에게 보내지 않지만, 재접속 뒤 재조회 범위가 없다. | B가 분석 결과를 기다리는 화면에 남거나 이미 준비된 결과를 놓친다. |
| A에서 개인 기록 삭제 후 B가 재접속 | `private_record.deleted`를 놓친 B의 삭제 확인 경로가 없다. | 삭제한 개인 기록이 B에 남아 보일 수 있다. |
| 같은 방에서 공용 메시지만 여러 건 발생 | `room_revision`의 간격만으로는 개인 변경의 존재·순서를 알 수 없다. | 공용 복구는 성공해도 개인 화면의 최신성을 보장할 수 없다. |

## 3. 보완 목표와 원칙

1. 방 공용 순번과 비공개 순번을 섞지 않는다.
2. 비공개 변경은 작성자 본인의 모든 로그인 기기에만 동기화한다.
3. 실시간 이벤트를 놓쳐도 서버 조회만으로 최신 비공개 상태를 복구할 수 있어야 한다.
4. 삭제된 개인 기록의 본문·AI 결과를 복구 응답이나 이벤트에 다시 포함하지 않는다.
5. 이 보완은 같은 초안을 동시에 수정할 때의 충돌 해결(R02)을 결정하지 않는다.

## 4. 확정 보완안

### 4.1 사용자·방 단위 비공개 순번

`user_room_private_state`를 논리 상태로 둔다.

| 필드 | 의미 |
| --- | --- |
| `user_id` | 비공개 데이터를 읽을 수 있는 작성자 |
| `room_id` | 해당 대국방 |
| `private_revision` | 이 사용자·방의 비공개 변경마다 1씩 증가하는 순번 |
| `updated_at` | 마지막 비공개 변경 시각 |

`private_revision`은 방의 `room_revision`과 독립적이다. 상대방에게 보낼 공용 이벤트에는 넣지 않는다.

### 4.2 비공개 변경 목록

재접속 뒤 누락된 변경을 판별할 수 있도록 `private_revision`별 최소 변경 메타데이터를 보관한다. 본문·AI 추천·안내 문구는 이 목록에 중복 저장하지 않는다.

| 필드 | 의미 |
| --- | --- |
| `user_id`, `room_id`, `private_revision` | 비공개 변경의 소유자·범위·순번 |
| `event_type` | `draft.updated`, `analysis.updated`, `private_record.deleted` 등 |
| `resource_type`, `resource_id` | 최신 상태를 조회할 대상 |
| `occurred_at` | 서버 확정 시각 |

개인 기록 삭제는 삭제 사실과 대상 식별자만 남기며, 삭제된 초안 본문과 AI 결과는 다시 반환하지 않는다.

### 4.3 저장과 실시간 전송

초안 저장, AI 분석 상태 변경, 개인 기록 삭제가 성공할 때 서버는 한 성공/실패 단위에서 다음을 처리한다.

1. 원본 비공개 데이터를 저장하거나 삭제 상태로 전환한다.
2. 해당 사용자·방의 `private_revision`을 증가시킨다.
3. 최소 변경 메타데이터를 기록한다.
4. 저장 성공 뒤에만 작성자의 접속 중인 모든 기기로 `private.*` 이벤트를 보낸다.

이벤트에는 `room_id`, `private_revision`, `event_type`, `resource_id`를 넣는다. 상세 본문은 이벤트가 아니라 작성자 인증이 필요한 조회 응답으로 가져온다.

### 4.4 재접속 복구 절차

클라이언트는 방 공용 순번과 별도로 마지막 적용 `private_revision`을 사용자·방 단위로 보관한다.

```text
재접속
→ room_revision 이후 공용 변경 조회
→ private_revision 이후 비공개 변경 조회
→ 누락 순번 없이 적용
→ 누락분 보관 기간 밖이거나 간격이 있으면 비공개 최신 스냅샷 조회
```

- 비공개 변경 조회는 요청 사용자 본인의 데이터만 반환한다.
- 순번이 연속되지 않거나 변경 목록이 보관 기간 밖이면, 서버는 작성 중 초안·현재 AI 분석 상태·삭제 표식을 포함한 최신 비공개 스냅샷을 반환한다.
- 클라이언트는 더 작은 `private_revision`의 이벤트를 적용하지 않는다.
- 삭제 표식이 포함된 리소스는 화면과 로컬 캐시에서 제거하며, 이전 본문을 다시 표시하지 않는다.

## 5. 대안과 권장 이유

| 안 | 방식 | 장점 | 한계 |
| --- | --- | --- | --- |
| A | 재접속 때마다 비공개 최신 스냅샷만 조회 | 구현이 가장 단순하다. | 어떤 변경을 놓쳤는지 알 수 없고, 실시간 여러 기기 화면의 순서 보장이 약하다. |
| B | 비공개 순번 + 변경 목록 + 스냅샷 폴백 | 실시간 누락 복구와 삭제 동기화를 모두 설명할 수 있다. | 변경 목록 보관·정리 정책이 필요하다. |

MVP에는 **B안**을 적용한다. 초안은 기기 전환을 지원하는 핵심 기능이고, 개인 기록 삭제는 다른 기기에도 즉시 반영돼야 하므로 단순 스냅샷만으로는 검증 기준을 만족하기 어렵다. 변경 목록의 보관 기간과 저장소 구현은 M1.3에서 정한다.

## 6. 재검증 시나리오와 완료 기준

| 시나리오 | 기대 결과 |
| --- | --- |
| A에서 초안 revision 3 저장, B가 재접속 | B는 `private_revision` 누락분을 조회해 revision 3의 최신 초안을 표시한다. |
| A에서 AI 심판이 `ready` 또는 `restricted`로 확정, B가 재접속 | B는 최신 분석 상태를 조회하며, `restricted`에는 추천 본문이 없다. |
| A에서 개인 기록 삭제, B가 재접속 | B는 삭제 표식을 적용해 초안·AI 결과를 표시하거나 캐시에서 복구하지 않는다. |
| B가 공용 메시지 누락과 비공개 변경 누락을 함께 겪음 | `room_revision`과 `private_revision`을 각각 복구해 두 흐름이 서로의 데이터를 노출하지 않는다. |
| 비공개 변경 목록이 만료됨 | 서버가 최신 비공개 스냅샷을 반환해 현재 상태를 복구한다. |

다음 조건을 모두 만족하면 P04를 문서상 해소로 바꾼다.

- 작성자 전용 변경마다 독립된 `private_revision`이 정의돼 있다.
- 이벤트 누락·순서 역전·변경 목록 만료 때의 조회 또는 스냅샷 복구가 정의돼 있다.
- 삭제된 개인 기록이 다른 기기에서 다시 보이지 않는 규칙이 정의돼 있다.
- 비공개 이벤트와 공용 이벤트의 수신자·순번·데이터가 분리돼 있다.

## 7. 후속 구현에서 정할 항목

- 비공개 변경 목록의 실제 보관 기간과 정리 방식
- 조회 API와 실시간 이벤트의 정확한 요청·응답 필드
- 동일 초안을 동시에 수정할 때의 충돌 정책(R02)
- M1.3에서 선택할 저장소·실시간 전송 수단에 따른 트랜잭션 구현 방식
