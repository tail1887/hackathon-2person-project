# R02 초안 동시 수정 충돌 보완계획

> 상태: 확정 · 기준 문서 반영 완료 · 2026-09-18

## 1. 목적과 범위

이 문서는 [M1.1 검증보고서 v2의 R02](../../2.%20검증보고서/M1.1/v2_검증보고서.md)인 **여러 기기에서 초안을 수정할 때의 충돌** 문제를 보완한다.

대상은 같은 로그인 계정이 같은 대국방의 작성 중 초안을 두 기기에서 수정·자동 저장·재접속하는 경우다. 서로 다른 사용자의 공동 문서 편집, 메시지 본문 병합, AI 분석 결과의 동시 편집은 범위에 포함하지 않는다.

## 2. 현재 문제 분석

현재 `message_draft.revision`은 수정마다 증가하고, `private_revision`은 여러 기기에 비공개 변경을 전달한다. 그러나 저장 요청이 어떤 초안 버전을 기준으로 작성됐는지와, 서버 버전이 이미 바뀌었을 때의 처리 규칙이 없다.

| 사례 | 현재 규칙의 공백 | 사용자 영향 |
| --- | --- | --- |
| A와 B가 revision 5 초안을 열어 각각 편집 | 두 저장 요청 중 늦게 도착한 요청을 구분할 기준이 없다. | A가 먼저 저장한 새 문장을 B의 오래된 자동 저장이 덮어쓸 수 있다. |
| B가 오프라인에서 편집한 뒤 재접속 | B의 보류 저장이 최신 초안인지 검증하지 않는다. | 재접속 순간 최신 내용이 유실될 수 있다. |
| B가 다른 기기의 저장 이벤트를 받음 | B에 아직 저장하지 않은 로컬 입력이 있을 때 화면을 무엇으로 갱신할지 없다. | 입력 중이던 문장이 사라지거나, 서버와 화면이 다른 내용을 보일 수 있다. |
| 충돌 뒤 사용자가 다시 저장 | 최신 서버 초안과 본인 입력 중 무엇을 기준으로 재시도할지 없다. | 사용자가 왜 저장되지 않았는지 알 수 없고 중복 저장을 반복할 수 있다. |

## 3. 보완 목표와 원칙

1. 오래된 자동 저장이 더 최신 초안을 조용히 덮어쓰지 못하게 한다.
2. 초안의 내용 버전(`message_draft.revision`)과 비공개 동기화 순번(`private_revision`)을 구분한다.
3. 충돌이 나도 사용자가 방금 입력한 로컬 문장을 잃지 않게 한다.
4. 충돌 해결은 작성자 본인의 로그인 기기에서만 보이며, 상대에게 초안·충돌 정보가 노출되지 않는다.
5. 글자 단위 자동 병합 대신, MVP에서 예측 가능하고 설명 가능한 재조회·명시적 재저장을 사용한다.

## 4. 권장 보완안

### 4.1 기준 버전 비교 저장

초안을 읽은 클라이언트는 마지막으로 서버에서 확정한 `message_draft.revision`을 `expected_revision`으로 보관한다. 자동 저장·수동 저장·버림·AI 심판 요청은 모두 이 기준 버전을 함께 보낸다.

서버는 작성자와 방을 확인한 뒤, 활성 초안의 현재 `revision`이 `expected_revision`과 같을 때만 요청을 적용한다.

```text
A와 B가 revision 5를 읽음
A가 expected_revision 5로 저장 → 성공, 서버 revision 6
B가 expected_revision 5로 저장 → 충돌, 서버 값은 바꾸지 않음
```

성공한 저장은 초안 본문·`revision` 증가·비공개 변경 목록·`private_revision` 증가를 하나의 성공/실패 단위로 처리한다. `private_revision`은 기기 동기화 순서이고, `revision`은 초안 내용의 기준 버전이므로 서로 대신할 수 없다.

### 4.2 충돌 응답과 화면 처리

기준 버전이 다르면 서버는 `draft_revision_conflict`를 반환한다. 이 응답은 작성자에게만 최신 서버 초안의 `revision`, 본문, 갱신 시각을 제공하고 기존 초안은 변경하지 않는다.

클라이언트는 자동 저장을 멈추고, 저장에 실패한 로컬 입력을 메모리 또는 기기 로컬 임시 상태에 보존한다. 사용자는 다음 중 하나를 선택한다.

| 선택 | 처리 |
| --- | --- |
| 최신 초안 사용 | 서버의 최신 본문·revision으로 작성창을 교체한다. 로컬 입력은 버린다. |
| 내 변경 적용 | 최신 서버 revision을 기준으로 로컬 입력을 다시 저장한다. 이 요청도 다시 충돌하면 최신 상태를 다시 보여 준다. |
| 직접 편집 | 최신 서버 본문을 바탕으로 사용자가 내용을 합친 뒤 저장한다. |

`내 변경 적용`은 사용자가 확인한 명시적 덮어쓰기일 뿐, 오래된 자동 저장이 자동으로 실행하는 동작이 아니다.

### 4.3 실시간 이벤트·재접속과 명령 경계

다른 기기에서 더 큰 `private_revision`의 `draft.updated` 이벤트를 받았을 때, 현재 기기에 저장하지 않은 입력이 없으면 최신 초안을 조회해 적용한다. 저장하지 않은 입력이 있으면 화면을 자동 교체하지 않고 충돌 안내와 최신 초안 조회를 제공한다.

오프라인 기기의 보류 저장도 재접속 뒤 원래의 `expected_revision`으로 보낸다. 서버가 거절하면 위 충돌 처리로 넘어간다.

초안 버전이 달라지면 해당 버전으로 요청한 AI 심판 분석은 기존 `stale` 규칙을 따른다. 전송은 이미 분석의 `draft_revision`과 현재 초안 버전이 같아야 하므로, 충돌 중인 오래된 초안으로 메시지를 전송할 수 없다.

## 5. 대안과 권장 이유

| 안 | 방식 | 장점 | 한계 |
| --- | --- | --- | --- |
| A | 마지막으로 도착한 저장을 항상 적용 | 구현이 가장 단순하다. | 늦은 자동 저장이 최신 문장을 조용히 덮어쓸 수 있다. |
| B | 기준 버전 비교, 충돌 시 재조회·명시적 재저장 | 최신 문장을 보호하고 충돌 원인·선택지를 사용자에게 설명할 수 있다. | 충돌 화면과 요청·응답 규칙이 추가된다. |
| C | 글자 단위 자동 병합(OT·CRDT) | 동시 편집 문서를 매끄럽게 병합할 수 있다. | 한 사용자의 개인 초안에는 구현·운영 복잡도가 과도하다. |

MVP에는 **B안**을 권장한다. 초안은 작성자 한 사람의 비공개 데이터이므로 공동 문서 수준의 자동 병합보다, 최신 서버 값을 보호하고 사용자가 명시적으로 결정하게 하는 방식이 적합하다.

## 6. 재검증 시나리오와 완료 기준

| 시나리오 | 기대 결과 |
| --- | --- |
| A와 B가 revision 5를 열고 A가 먼저 저장 | A의 저장만 성공하고 서버 초안은 revision 6이 된다. |
| B의 revision 5 자동 저장이 늦게 도착 | 서버는 `draft_revision_conflict`를 반환하고 revision 6 본문을 바꾸지 않는다. |
| B가 최신 초안 사용을 선택 | B의 작성창은 revision 6 서버 본문으로 바뀌며 이후 저장은 revision 6을 기준으로 한다. |
| B가 내 변경 적용을 선택 | B는 최신 revision을 기준으로 다시 저장한다. 성공하면 새 revision이 되고, 다시 충돌하면 자동 덮어쓰기 없이 최신 상태를 다시 제시한다. |
| B가 오프라인 편집 뒤 재접속 | 보류 저장도 원래 `expected_revision`으로 검사되며, 충돌 시 B의 로컬 입력이 사라지지 않는다. |
| B가 로컬 입력 중 A의 `draft.updated` 이벤트 수신 | B의 화면은 자동 교체되지 않고 충돌 해결 선택지를 표시한다. |
| 충돌 중 B가 기존 AI 심판 결과로 전송 시도 | 현재 초안 revision과 분석 revision이 다르므로 서버가 전송을 거절한다. |

다음 조건을 모두 만족하면 R02를 문서상 해소로 바꾼다.

- 초안 변경 명령에 `expected_revision` 비교가 정의돼 있다.
- 충돌 때 서버가 기존 본문을 바꾸지 않고 작성자에게만 최신 초안을 반환한다.
- 자동 저장·실시간 이벤트·재접속에서 로컬 미저장 입력을 잃지 않는 규칙이 정의돼 있다.
- 초안 내용 버전과 `private_revision`의 역할이 분리돼 있다.

## 7. 후속 구현에서 정할 항목

- 충돌 화면의 문구와 `최신 초안 사용`·`내 변경 적용`·`직접 편집` 버튼 배치
- 로컬 임시 입력의 보관 기간과 앱 종료 뒤 복구 범위
- M1.2 인터페이스 계약의 `expected_revision`, `draft_revision_conflict`, 최신 초안 응답 필드
- M1.3에서 선택할 저장소·실시간 전송 수단에 따른 조건부 갱신과 트랜잭션 구현 방식
