## 2. 구현 경계

- 브라우저는 Supabase Auth 세션으로 본인을 증명하고, 읽기가 허용된 상태를 조회·구독한다. 클라이언트 입력과 화면 상태는 확정 사실이 아니다.
- 방·초대·메시지·협상·미션·AI 문철처럼 상태를 바꾸는 명령은 Supabase Edge Function에서 인증·방 멤버·현재 상태·순번을 검증한 뒤 처리한다. 여러 기록을 함께 바꾸는 명령은 Postgres 트랜잭션/RPC로 하나의 성공·실패 단위로 확정한다.
- 확정 저장 뒤에만 Realtime Broadcast로 공용 또는 작성자 전용 변경 알림을 보낸다. 데이터베이스가 기준이며, 이벤트 누락 시 M1.2 계약의 `room_revision`·`private_revision` 조회·스냅샷 복구를 사용한다.
- OpenAI 호출은 Edge Function에서만 한다. OpenAI API 키·Supabase service role 키·OAuth 제공자 비밀값은 브라우저와 저장소에 넣지 않는다. OpenAI는 Responses API를 사용하며, 모델명·프롬프트 세부값·요청 비용 상한은 실제 AI 기능 구현 전에 별도 설정으로 고정한다.

## 3. 인증과 제외 범위

- 제공 로그인: 카카오, 구글, 이메일·비밀번호.
- 제외: 네이버 로그인, 사진 첨부, 사진 인증, 파일 저장소와 이미지 AI 판별.
- 초대 링크와 6자리 코드는 로그인 뒤에만 검사하며, 로그인 전에는 초대 정보가 노출되지 않는다.

## 4. M1.2 계약 충족 근거

| 계약 요구 | 선택한 구현 경로 |
| --- | --- |
| 방 멤버만 읽기·변경 | Supabase Auth 세션 + Postgres RLS + Edge Function의 재검증 |
| 협상 합의의 방 종료·미션 생성 원자 처리 | Edge Function 명령 + Postgres 트랜잭션/RPC |
| 공용·비공개 순번과 복구 | Postgres 기준 순번 + 권한 있는 Realtime Broadcast + 조회·스냅샷 |
| AI 공개 범위 분리 | Edge Function이 분석 종류와 수신 범위를 확인한 뒤 결과를 저장·발행 |
| 30초 복구 정책 | Next.js 클라이언트가 재연결 뒤 제한 시간 동안 조회 복구, 이후 읽기 전용·수동 재시도 |

Supabase는 Auth·Postgres·RLS·Realtime·Edge Functions를 제공하고, Realtime Broadcast의 권한 제어를 지원한다. [Supabase 개요](https://supabase.com/docs) · [Realtime 권한](https://supabase.com/docs/guides/realtime/authorization) OpenAI API 키는 서버 환경 변수 또는 키 관리 서비스에서만 로드해야 하므로 Edge Function 경계에 둔다. [OpenAI API 인증](https://platform.openai.com/docs/api-reference/authentication)

## 5. 대안과 선택 이유

- 분리 서버 조합은 세밀한 제어는 가능하지만 서버·실시간·인증 운영 지점이 늘어 2인 해커톤의 빠른 개발 목표와 맞지 않는다.
- Firebase 중심 조합은 실시간 시작은 빠르지만 협상 이력·미션·권한의 관계형 모델과 원자 전이를 다시 설계해야 한다.
- 따라서 기존 시스템 계약과 가장 가까우면서 관리 서비스를 최소화하는 통합 Postgres 조합을 선택한다. Vercel은 Next.js의 Git 기반 미리보기 배포를 지원하므로 데모 검증에도 맞는다. [Vercel Next.js 배포](https://vercel.com/docs/frameworks/full-stack/nextjs)
