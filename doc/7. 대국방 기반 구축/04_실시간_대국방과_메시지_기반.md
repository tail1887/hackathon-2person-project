# M2 페이즈 4 — 실시간 대국방과 메시지 기반

> 상태: 구현 완료 · 원격 Realtime 설정·사용자 검증 대기 · 2026-09-20

## 목적과 범위

방 멤버 두 사람이 대국방에서 같은 공용 상태를 보고, 상대 입장과 공용 메시지 순서를 실시간으로 반영하게 한다.

## 구현 항목

- 대국방 초기 스냅샷: 멤버, 방 상태, 메시지 목록, 최신 `room_revision`
- 초대 대기: 링크·코드·상대 입장 대기, `room.member_joined` 수신 뒤 대국방 전환
- 공용 메시지 저장·조회와 `message.sent` 이벤트의 순서 반영
- Supabase Realtime Broadcast 채널 구독과 멤버 검증
- 마지막 적용 `room_revision` 이후 변경 조회, 단절 시 스냅샷 교체
- 연결 복구 중 마지막 확정 공용 상태 읽기 전용 유지, 30초 실패 시 수동 재시도·메인 복귀

## 메시지 전송 경계

M2는 저장·동기화 기반을 검증하지만 일반 사용자에게 직접 전송 버튼을 노출하지 않는다. M3에서 `message.send`에 최신 AI 분석·원문 해시·원문/추천 선택 검증을 결합해 제품 전송으로 연다. M2의 메시지 이벤트는 통합 테스트·개발용 서버 호출로만 생성한다.

## 테스트와 완료 기준

- 서로 다른 브라우저의 A·B가 같은 방에서 상대 입장과 공용 메시지를 같은 순서로 확인한다.
- 늦게 열린 브라우저·일시 연결 단절 뒤에도 순번 중복·역전 없이 최신 상태로 복구한다.
- 방 밖 사용자와 작성자 전용 데이터는 Broadcast payload에 포함하지 않는다.

## 구현 결과와 외부 설정 요청

- `room_public`, `room_member_public`, `room_message_public`으로만 대국방 초기·복구 스냅샷을 읽는 화면을 구현했다. 내부 `user_id`와 초안·AI 분석은 브라우저 조회와 화면에 포함하지 않는다.
- 대국방 채널은 `room:{room_id}`, 초대 대기 채널은 `invite:{invite_id}`를 사용한다. `realtime.messages` 정책은 방 멤버 또는 해당 초대의 생성자·수락자만 Broadcast를 받을 수 있게 제한한다.
- 메시지가 서버에 확정되면 트리거가 `room_revision`을 올리고, 방 전용 공개 키·순번·시각만 담은 `message.sent` Broadcast를 보낸다. 제품 화면에는 M3 전까지 메시지 전송 버튼을 만들지 않았다.
- 초대 수락 트랜잭션은 두 멤버와 방을 확정한 뒤, 생성자의 초대 대기 화면과 방 채널에 `room.member_joined` Broadcast를 보낸다. 수신 화면은 항상 공개 스냅샷을 다시 읽어 이벤트 누락·역순을 복구한다.
- 연결 단절은 마지막 확정 상태를 읽기 전용으로 유지하고 2초 간격으로 최대 30초 스냅샷 복구를 시도한다. 실패하면 수동 재시도·메인 복귀만 제공한다.

원격 반영 전 프로젝트 소유자는 `20260920000600_add_room_realtime_broadcast.sql`을 적용하고, Supabase **Realtime Settings**에서 공개 채널을 끈 뒤 비공개 채널을 사용해야 한다. 이후 서로 다른 A·B·제3 사용자로 초대 대기 전환·입장·메시지 순서·30초 복구·비멤버 구독 차단을 검증한다.
