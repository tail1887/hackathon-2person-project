# M2 페이즈 3 — 방·초대·권한과 명령

> 상태: 초대 대기 모델 원격 배포 완료 · 실사용자 권한 검증 대기 · 2026-09-20

## 목적과 범위

대국방과 초대의 최소 스키마·RLS·원자 명령을 구현해, 두 명 제한과 방 밖 비공개를 데이터 계층에서 강제한다.

## 데이터·권한 단위

| 대상 | M2 최소 책임 | 권한 원칙 |
| --- | --- | --- |
| `profiles` | 표시 이름·인증 사용자 연결 | 본인만 수정, 방에서는 방 전용 표시 정보만 노출 |
| `rooms` | `active`·`closed`, 공용 순번 | 멤버만 조회 |
| `room_members` | `creator`·`invitee`, 두 명 제한 | 같은 방 멤버만 조회 |
| `pending_invites` | 비밀 링크 토큰·6자리 코드·사용 상태 | 수락 명령 외 원문 비공개; 대국방 생성 전에는 방이 없음 |
| `messages` | 순서·발신자 방 전용 키·본문·시각 | 방 멤버만 조회 |

## 명령 경계

- `room.create`: 로그인 사용자가 Edge Function으로만 호출한다. 진행 중 방이 있으면 `active_room_exists`를 반환하고, 없으면 방 없이 활성 초대 대기를 발급한다. 같은 생성자의 활성 초대가 있으면 이전 링크·코드를 새 값으로 재발급한다.
- `invite.accept`: 로그인 뒤 링크 토큰 또는 코드로 Edge Function을 호출한다. 유효성·생성자와 호출자의 진행 중 방을 확인한 뒤 새 방·두 멤버·초대 사용을 하나의 트랜잭션으로 확정한다.
- 실패 응답은 `invite_expired_or_revoked`, `invite_used_or_full`, `active_room_exists`, `invalid_invite` 중 안전한 안내 키만 반환하며 방 내부 정보는 포함하지 않는다.
- `room.snapshot.get`, `room.changes.get`: 멤버만 호출한다. 공용 `room_revision` 단절 시 최신 스냅샷을 반환한다.

## 테스트와 완료 기준

- A·B 동시 수락 시도, 이미 사용된 초대, 이미 다른 진행 중 방이 있는 생성자 또는 B를 각각 검증한다.
- 제3 사용자의 직접 테이블 조회·변경, 다른 방 ID·초대 추측, 클라이언트에서 상태 변경 호출을 모두 RLS·명령 권한에서 막는다.
- M1.2 계약의 오류 코드와 화면 안내가 일치한다.

## 구현 결과

- `20260920000200_create_rooms_and_invites.sql`에 초기 `rooms`, `room_members`, `invites`, `messages`와 멤버 확인용 `is_room_member` 함수, 공개 조회용 `room_public`·`room_member_public`·`room_message_public` 뷰를 추가했다. 멤버 확인은 재귀 없는 security definer 함수로 처리한다.
- `20260920000300_revoke_room_base_table_privileges.sql`와 `20260920000400_revoke_room_public_view_mutations.sql`로 브라우저 역할의 원본 테이블 권한을 모두 회수하고, 공개 뷰에는 `authenticated`의 `SELECT`만 다시 부여한다. 따라서 브라우저는 내부 `user_id`가 있는 원본 테이블을 직접 조회·변경할 수 없다.
- `20260920000500_create_pending_invites.sql`은 기존 테스트용 `waiting` 방을 정리하고, 방 없는 `pending_invites`와 `create_pending_invite`·`accept_pending_invite` RPC로 전환한다. 수락 성공 때만 방·두 멤버·초대 사용을 함께 확정한다.
- `room-create`, `invite-accept` Edge Function과 메인의 초대 발급·코드 입장·링크 수락 UI를 연결했다. 실제 대국방 상태 조회·상대 입장 실시간 반영은 페이즈 4에서 추가한다.
- 두 Edge Function은 `OPTIONS` CORS 사전 요청을 허용하고, 플랫폼의 요청 전 JWT 검사를 쓰지 않는 대신 실제 `POST`에서 Supabase Auth의 토큰 검증을 통과해야만 RPC를 실행한다. 따라서 브라우저 호출 호환성과 방 상태 변경 인증 경계를 함께 유지한다.
- `20260920000500_create_pending_invites.sql`과 새 `room-create`·`invite-accept` 함수를 운영 Supabase에 배포했다. 기존 테스트용 `waiting` 방·멤버·메시지·초대는 0건으로 정리했고, 로그인 계정·프로필은 각각 3건으로 보존됐다. 다음으로 A·B·제3 사용자 시나리오를 재검증한다.
- 배포 전에는 원본 테이블 직접 `select` 거부, 공개 뷰의 멤버 전용 조회, A·B 상호 조회에 `user_id`가 없는지까지 확인한다.
