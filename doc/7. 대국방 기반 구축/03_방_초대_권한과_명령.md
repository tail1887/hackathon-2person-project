# M2 페이즈 3 — 방·초대·권한과 명령

> 상태: 코드 구현 완료 · 원격 DB·명령 배포 대기 · 2026-09-20

## 목적과 범위

대국방과 초대의 최소 스키마·RLS·원자 명령을 구현해, 두 명 제한과 방 밖 비공개를 데이터 계층에서 강제한다.

## 데이터·권한 단위

| 대상 | M2 최소 책임 | 권한 원칙 |
| --- | --- | --- |
| `profiles` | 표시 이름·인증 사용자 연결 | 본인만 수정, 방에서는 방 전용 표시 정보만 노출 |
| `rooms` | `waiting`·`active`, 공용 순번 | 멤버만 조회 |
| `room_members` | `creator`·`invitee`, 두 명 제한 | 같은 방 멤버만 조회 |
| `invites` | 비밀 링크 토큰·6자리 코드·사용 상태 | 수락 명령 외 원문 비공개 |
| `messages` | 순서·발신자 방 전용 키·본문·시각 | 방 멤버만 조회 |

## 명령 경계

- `room.create`: 로그인 사용자가 Edge Function으로만 호출한다. 진행 중 방이 있으면 `active_room_exists`를 반환하고, 없으면 `waiting` 방·생성자 멤버·활성 초대를 함께 만든다.
- `invite.accept`: 로그인 뒤 링크 토큰 또는 코드로 Edge Function을 호출한다. 유효성·빈자리·호출자의 진행 중 방을 확인한 뒤 멤버 생성·초대 사용·방 `active`를 하나의 트랜잭션으로 확정한다.
- 실패 응답은 `invite_expired_or_revoked`, `invite_used_or_full`, `active_room_exists`, `invalid_invite` 중 안전한 안내 키만 반환하며 방 내부 정보는 포함하지 않는다.
- `room.snapshot.get`, `room.changes.get`: 멤버만 호출한다. 공용 `room_revision` 단절 시 최신 스냅샷을 반환한다.

## 테스트와 완료 기준

- A·B 동시 수락 시도, 이미 두 명인 방, 이미 다른 진행 중 방이 있는 B를 각각 검증한다.
- 제3 사용자의 직접 테이블 조회·변경, 다른 방 ID·초대 추측, 클라이언트에서 상태 변경 호출을 모두 RLS·명령 권한에서 막는다.
- M1.2 계약의 오류 코드와 화면 안내가 일치한다.

## 구현 결과

- `20260920000200_create_rooms_and_invites.sql`에 `rooms`, `room_members`, `invites`, `messages`와 멤버 전용 조회 RLS를 추가했다. 초대 원문·브라우저 직접 쓰기 정책은 제공하지 않는다.
- `create_room_with_invite`와 `accept_invite` RPC는 사용자별 advisory lock과 방 행 잠금으로 진행 중 방 하나·방당 두 명·수락 원자 처리를 보장한다. 수락 실패는 계약의 네 안전한 오류 코드만 반환한다.
- `room-create`, `invite-accept` Edge Function과 메인의 방 생성·코드 입장·링크 수락 UI를 연결했다. 실제 대국방 상태 조회·상대 입장 실시간 반영은 페이즈 4에서 추가한다.
- 프로젝트 소유자는 원격 Supabase에 마이그레이션과 두 Edge Function을 배포한 뒤 A·B·제3 사용자 시나리오를 실행해 이 문서의 완료 기준을 검증한다.
